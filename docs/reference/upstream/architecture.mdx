## The single-port CLI

This is what `mtmux` runs and what almost everyone uses. One Node process, one
HTTP server, everything same-origin.

```
  Browser  ⇄ http/ws ⇄  mtmux (one process)  ⇄ pty ⇄  tmux
              one port   Next.js + relay              your sessions
```

The HTTP server serves the bundled Next.js web client, and the relay attaches
its WebSocket upgrade handler at **`/_relay`**. Because it is one origin there
is no CORS to configure, no `NEXT_PUBLIC_RELAY_URL`, and one thing to put behind
a reverse proxy.

Inside the published package the layout is:

```
dist/bin.js               the whole CLI, bundled by esbuild
dist/web/apps/web/…       the Next standalone server for the web client
dist/relay/runtime.js     the relay, bundled
```

## Adding a device that is not on your network

The picture grows two components: a **blind broker** (`apps/api`) and a
**reverse tunnel agent** that lives inside the CLI process.

```
                            api.mtmux.com
                          ┌────────────────┐
                          │  pairing       │   routes claims, holds mailboxes
                          │  mailboxes     │
   Browser ───────────────┤                ├──────────────── mtmux
   (app.mtmux.com)        │  tunnel relay  │   forwards sealed frames only
        │                 └────────────────┘                   │
        │                                                      │
        └──────────── direct path, raced first ────────────────┘
                     ws://192.168.1.5:14100/_relay
```

Two paths, chosen at runtime:

- **Direct.** The browser races the candidate addresses the CLI sealed into the
  pairing descriptor. A candidate wins by completing the relay auth handshake
  with the PAKE-derived token — not by answering an HTTP probe, which a captive
  portal can fake. Timeout 800 ms.
- **Tunnel.** If no candidate wins, the browser opens `WS /v1/tunnel/:id` on the
  broker and wraps every relay line in an AES-256-GCM frame. The broker forwards
  ciphertext and holds no key.

The full cryptographic story is in [The sealed tunnel](/docs/sealed-tunnel).

### Why the agent, and not the relay

The tunnel agent opens an ordinary local WebSocket to
`ws://127.0.0.1:<port>/_relay`, authenticates it with the machine's own token,
and copies relay protocol lines between there and the broker — unsealing what
comes from the browser and sealing what goes back.

The isolation is the point. The relay sees a perfectly normal authenticated
local client and knows nothing about tunnels, brokers, pairing or AES, so
nothing in the hosted path can regress the self-hosted one. It also means the
64-hex `AUTH_TOKEN` is injected on the machine's side of the tunnel and never
travels over it.

## The split model

For containers, PM2 and multi-tenant deployments the same code runs as separate
services.

```
  Browser ─┬─ https ──► apps/web    (Next.js, 14100)
           └─ wss ────► apps/relay  (14300)
```

The browser is told where the relay is with `NEXT_PUBLIC_RELAY_URL`, and the
reverse proxy routes a dedicated `/ws` location to it. See
[Deployment](/docs/deployment).

## Repository map

| Path | What it is |
| --- | --- |
| `apps/cli` | The published **`mtmux`** package. Bundles web + relay into one process. Also hosts `scripts/dev.mjs`, the single-port dev server behind `pnpm dev`. |
| `apps/web` | Terminal web client — Next.js 16, React 19, xterm.js. Port 14100. |
| `apps/relay` | WebSocket relay to tmux via PTY. Served at `/_relay` in CLI mode; port 14300 in split mode. |
| `apps/api` | The blind pairing broker and tunnel relay. Port 14400 by default. |
| `apps/docs` | This site. Next.js + Fumadocs, port 14102. |
| `apps/site` | The marketing site at mtmux.com. |
| `packages/protocol` | Zod message schemas — relay protocol *and* pairing/tunnel protocol. |
| `packages/crypto` | CPace, the HKDF key schedule, sealed frames, device keys, pairing codes. |
| `packages/db` | Database schema for the hosted accounts layer. |
| `packages/ui` | shadcn/ui components + terminal themes. |
| `packages/logger` | Pino logger. |
| `packages/config` | Shared env + constants. |

Everything is ESM (`"type": "module"`), internal packages are `@repo/*` and apps
are `@app/*` — except the CLI, whose package name is its npm name, `mtmux`.

## Data flow, end to end

1. The browser authenticates by sending an `auth` message as the **first**
   message on the socket, within 5 seconds.
2. The relay answers `auth:success` plus a `server:info` frame.
3. The client requests `session:list` and attaches with `session:attach`.
4. The relay spawns a PTY attached to that tmux session.
5. Keystrokes go browser → relay → PTY as `terminal:input`; output comes back as
   `terminal:output`.
6. `terminal:resize` propagates size changes to the PTY.

On a tunnelled session every one of those lines is sealed before it reaches the
broker and unsealed by the agent, so steps 2–6 are byte-identical from the
relay's point of view.

## Web client structure

```
(terminal)/layout.tsx      → auth guard, transport selection, WebSocket init, app shell
  └─ (terminal)/page.tsx   → sidebar + terminal + file panel
       ├─ TerminalToolbar  → session name, search, fullscreen, settings
       ├─ TerminalView     → the xterm.js instance, attach/detach lifecycle
       ├─ SessionList      → session cards: create, attach, rename, kill
       └─ FileTree         → directory browser, editor, previews
```

State lives in Zustand stores under `apps/web/src/stores/`:

| Store | Holds | Persisted |
| --- | --- | --- |
| `connection-store` | Status, latency, reconnect count, server info | No |
| `session-store` | Session list, active session, open desktop tabs | No |
| `pane-store` | Windows, panes, active and zoomed pane | No |
| `terminal-store` | Font, theme, cursor, scrollback, GPU rendering | Yes |
| `file-store` | Current path, entries, editor and viewer state | No |
| `command-store` | Command history and snippets | Yes |
| `settings-store` | Toolbar keys, gestures, haptics, auto-zoom | Yes |
| `ui-store` | Mobile tab, sheets, overlays, sidebar | No |
| `alert-store` | The in-app alert queue | No |

## Relay structure

```
apps/relay/src/
├─ server.ts            HTTP routes: /health, /_pair/local, /_pair/session, /file
├─ ws-server.ts         WebSocket upgrade, origin checks, payload cap
├─ wire-connections.ts  auth deadline, rate limit, ping/pong, idle reaper
├─ auth.ts              token comparison (timing-safe), throttle integration
├─ auth-throttle.ts     failed-auth lockout, per address
├─ pairing-local.ts     LAN sign-in nonces and scoped session tokens
├─ message-router.ts    routes authenticated messages to handlers
├─ tmux-manager.ts      tmux CLI operations
├─ pty-bridge.ts        node-pty attached to tmux sessions
├─ file-service.ts      file operations with path allow-listing
└─ config.ts            Zod-validated environment configuration
```

See [Relay server](/docs/relay).

## Broker structure

```
apps/api/src/
├─ server.ts       HTTP routes + WebSocket routing
├─ broker.ts       mailboxes, claims, fan-out, key confirmation relaying
├─ mailbox.ts      pending pairings, indexed by slot
├─ tunnel.ts       live tunnels, streams and quotas
├─ rate-limit.ts   per-key sliding windows
└─ config.ts       Zod-validated environment configuration
```

Pairing and tunnelling — always available:

| Route | Method | Purpose |
| --- | --- | --- |
| `/health` | GET | Liveness |
| `/v1/discover` | GET | Tell a machine what public address it appears to come from |
| `/v1/pair/new` | POST | Park a mailbox, get a slot |
| `/v1/pair/claim` | POST | Quote a slot, get a claim handle |
| `/v1/pair/:mailboxId` | WS | The mailbox holder's socket |
| `/v1/claim/:claimId` | WS | The claimant's socket |
| `/v1/agent` | WS | A CLI registering its reverse tunnel |
| `/v1/tunnel/:id` | WS | A browser opening a stream on one |

Accounts and billing — **optional**, and answering `503` when `DATABASE_URL` is
unset:

| Route | Method | Purpose |
| --- | --- | --- |
| `/api/auth/*` | — | better-auth, including the device-authorization grant behind `mtmux login` |
| `/v1/me` | GET | The signed-in account and its plan |
| `/v1/servers` | GET | Machines on the account |
| `/v1/servers/register` | POST | Claim a registry row for this machine |
| `/v1/servers/:id/heartbeat` | POST | Liveness, every 30 s from a signed-in server |
| `/v1/servers/:id` | PATCH, DELETE | Rename or remove a machine |
| `/v1/billing` | GET | Current plan and usage |
| `/v1/billing/checkout` | POST | Start a checkout |
| `/v1/billing/portal` | POST | Open the billing portal |

These are dispatched before the pairing routes and fall through to them when the
path is not one of theirs. A broker with accounts off still serves every route
in the first table.

The rate limits are not polite capacity management — they carry part of the
security argument. The one-shot guessing bound in
[How pairing works](/docs/pairing) assumes an attacker cannot spray claims
across every slot, and the mailbox limit stops one client filling every slot to
raise its odds of a collision.

## Protocol

Two separate pairs of discriminated unions, deliberately not merged:

- **Relay protocol** — `client-messages.ts` and `server-messages.ts`. Terminals,
  sessions, panes, windows, files, commands. 44 client types, 24 server types.
- **Pairing and tunnel protocol** — `pairing-messages.ts`. Travels between the
  browser/CLI and the broker, never over the relay socket.

Folding them together would imply the relay understands pairing (it does not)
and that the broker understands terminals (it must not). See
[Protocol reference](/docs/relay/protocol).
