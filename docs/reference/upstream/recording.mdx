---
title: Recording a Session
description: Capture a tmux session or a single pane to a file on your own machine, play it back in the browser, and hand a copy to someone.
---

`mtmux record` writes what happens in a tmux session — or in one pane — to an
[asciinema v2](https://docs.asciinema.org/manual/asciicast/v2/) `.cast` file
under `~/.mtmux/recordings/`. Nothing is uploaded. The file is yours, and the
broker is never told it exists.

```bash
mtmux record work
```

```
  ● Recording work  120×40
    rec_k3m9x2p7q4wvtn8s

    A recording contains everything printed on screen, including
    anything secret. The file is yours alone (0600).

    Stop with mtmux record stop rec_k3m9x2p7q4wvtn8s
```

## What a recording contains

Everything that was on the screen, and nothing else.

- **Output only.** asciinema's format has an input event type. mtmux never
  writes one, so a recording is not a keylogger — it is what you would have seen
  over the shoulder of whoever was at the terminal.
- **Every secret that was printed.** An API key echoed by a misconfigured tool,
  a token in a `curl` command, the contents of a `.env` you `cat`'d. There is no
  redaction pass and there is not going to be a convincing one: a terminal
  stream is not structured, and a filter that catches four secret formats out of
  five is worse than no filter, because it invites trust it has not earned.
- **`TERM`, and the title you gave it.** Not `SHELL`, not your environment, not
  your username. The header is deliberately thin, because it travels with the
  file.

The file is created `0600` in a `0700` directory. Read it before you share it.

## Recording a session

```bash
mtmux record work                    # the session called "work"
mtmux record work --title "the refactor"
```

mtmux attaches a second, locked tmux client to a grouped clone of the session —
the same mechanism a read-only share uses. That client is sized to whatever the
session is already at and has `aggressive-resize` off, so starting a recording
never resizes the panes you are looking at.

Because a tmux client forces a full redraw when it attaches, the recording opens
on the complete screen as it stood, with the right cursor position, colours and
alternate-screen state.

## Recording one pane

```bash
mtmux record work --pane %7
```

This uses `tmux pipe-pane`, which is the right tool for "record what my agent
did in that pane" and has two honest limitations:

- **It starts mid-stream.** `pipe-pane` copies what the pane writes from now on
  and knows nothing about what is already on screen, so mtmux writes a clear and
  the pane's current contents as the first frame. That frame is a snapshot, not
  a replay: scrollback above it is not in the recording.
- **One pipe per pane.** Starting a second `pipe-pane` on a pane silently
  replaces the first, so mtmux refuses rather than clobbering a pipe you set up
  yourself. Stop yours, or record a different pane.

## Listing, stopping and deleting

```bash
mtmux record list
mtmux record list --json
mtmux record stop rec_k3m9x2p7q4wvtn8s
mtmux record stop --all
mtmux record rm rec_k3m9x2p7q4wvtn8s
```

`rm` deletes the file as well as the index row.

## Limits

Two per recording, one across all of them. These are safety limits, not plan
limits — recordings are files on your own disk and cost us nothing, so nothing
here is metered and nothing here needs an account.

| Limit | Value | Why |
| --- | --- | --- |
| Size | 16 MiB | Seeking is linear in bytes (see below). Past this, scrubbing stops feeling instant. |
| Duration | 4 hours | Long enough for the agent run this exists for; not open-ended. |
| Total on disk | 1 GiB | Swept oldest-first at startup, so a `record` left running in July does not fill the disk. |

A recording that hits a limit stops **cleanly** and says so, in the CLI and in
the browser. A recording that silently stopped growing would read as a bug.

If the server is killed mid-recording, the next start closes the row from what
made it to disk and marks it `cut off`. The `.cast` is still readable: the
parser drops a torn final line rather than refusing the whole file.

## Playing one back

Open `/r` in the web client. Recordings play in a real xterm, so they render
exactly as the session did — truecolor, powerline glyphs, box drawing and all.

Space plays and pauses, the arrow keys jump five seconds, and the speed control
cycles 0.5× → 1× → 2× → 4×.

Seeking backwards is the one slow operation. A terminal's state is a fold over
every byte before it, and there is no way to snapshot that fold, so jumping back
means replaying the recording from the start to that point. It is why the size
cap is what it is.

## Sharing one

```bash
mtmux record share rec_k3m9x2p7q4wvtn8s --expires 7d
```

Same pairing code, same sealed tunnel and same grant machinery as
[`mtmux share`](/docs/sharing). What differs is the warning, because the risk is
different in kind:

```
  Sharing 1 recording · read-only · no file access · expires in 7 days

  They get a copy. Once their browser has downloaded it, revoking the
  share does not take it back.
  A recording contains everything that was on screen, including anything
  secret that was printed.
```

A recordings share is a real boundary in the way a read-write session share is
not. The grant's scope names recordings and nothing else, so the connection can
attach to no session, send no input and read no files — the relay refuses every
message type outside listing and fetching, whatever the client asks for.

What it is *not* is recall. Once the bytes are in someone's browser they are
theirs; `mtmux share revoke` stops future fetches and nothing more.

The broker still sees nothing. The `.cast` leaves your machine only as
AES-256-GCM frames under keys derived from a PAKE run between the two endpoints
— see [the sealed tunnel](/docs/sealed-tunnel).

## Where the files are

```
~/.mtmux/recordings/
  index.json                                        # id → filename, 0600
  20260903-174439-work-rec_k3m9x2p7q4wvtn8s.cast    # 0600
```

They are ordinary asciinema files. `asciinema play`, `agg` and
`asciinema-player` all read them, and a `.cast` you `scp` somewhere else works
there. Move `~/.mtmux/recordings` with `MTMUX_CONFIG_DIR`.
