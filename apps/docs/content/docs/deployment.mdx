## Pick a topology first

Choosing the wrong reverse-proxy wiring for your model is the most common
misconfiguration here, so pick one and do not mix them.

| | CLI, single port | Split web + relay |
| --- | --- | --- |
| Command | `mtmux` | Docker / PM2 |
| Processes | 1 | 2+ |
| WebSocket | same-origin at `/_relay` | separate service |
| `NEXT_PUBLIC_RELAY_URL` | **unset** | required |
| Proxy | everything to one port | `/ws` → relay, `/` → web |

In short: `/_relay` with no `NEXT_PUBLIC_RELAY_URL` is CLI mode; `/ws` plus
`NEXT_PUBLIC_RELAY_URL` is the split model. For a single machine, use the CLI —
see [Getting started](/docs/getting-started).

## The hosted deployment

`ecosystem.config.cjs` is the real thing this repository deploys, and it is
worth reading rather than paraphrasing. It defines **five** PM2 apps.

| App | Script | Port | Mode | Instances |
| --- | --- | --- | --- | --- |
| `mtmux-api` | `apps/api/dist/index.js` | 24400 | fork | 1 |
| `mtmux-relay` | `apps/relay/dist/index.js` | 24300 | fork | 1 |
| `mtmux-app` | `apps/web/.next/standalone/apps/web/server.js` | 24100 | cluster | 2 |
| `mtmux-docs` | `next start --port 24102` in `apps/docs` | 24102 | fork | 1 |
| `mtmux-web` | `next start --port 41317` in `apps/site` | 41317 | cluster | 2 |

Everything runs plain HTTP on loopback; TLS terminates at the edge and nginx
proxies to these ports. `app.mtmux.com` fronts `mtmux-app`, `api.mtmux.com`
fronts `mtmux-api`, `mtmux.com` fronts `mtmux-web`.

Four details in that file are load-bearing:

- **`mtmux-api` is fork mode with one instance.** The broker holds mailboxes,
  claims and live tunnel sockets in memory. A second worker would route a
  browser to a process that has never heard of its pairing.
- **`mtmux-app` runs `server.js`, not `next start`.** `apps/web` builds with
  `output: "standalone"` because the CLI needs it, and Next refuses to serve
  that tree via `next start` — it warns and then serves anyway, which is exactly
  the kind of half-working that survives a smoke test and fails in a browser.
- **`instances: 2`, not `"max"`.** The box has 32 cores but shares them with
  around twenty other services, and Next's workload here is light: terminal
  traffic rides the relay and the tunnel, not this process.
- **`API_CORS_ORIGINS` is set explicitly.** The broker refuses to boot in
  production if its CORS list still contains localhost.

`mtmux-app`'s env repeats `NEXT_PUBLIC_RELAY_URL` and `NEXT_PUBLIC_API_URL`
even though Next inlined them at build time. They are there so a stray value in
`.env` cannot make the running process disagree with the bundle it is serving.

## Deploying the hosted stack

Three commands, and the order matters because each failure looks like something
else.

```bash
pnpm deploy:hosted
```

That runs, in order:

```bash
pnpm build:hosted        # build with the API origin baked in
# verify the origin is actually in the client bundle
pnpm prepare:standalone  # copy .next/static and public/ into the standalone tree
pm2 reload mtmux-api mtmux-app --update-env
```

### Why each step exists

- **`pnpm build:hosted`.** A plain `pnpm build` bakes no `NEXT_PUBLIC_API_URL`
  into `apps/web` — Next inlines those at build time — so the pair page renders
  "not configured" and the CSP blocks the broker. It also picks up
  `NEXT_PUBLIC_RELAY_URL` from `.env`, pointing every visitor at
  `ws://localhost:14300` on their *own* machine. So the build must carry
  explicit env:

  ```bash
  NEXT_PUBLIC_RELAY_URL= NEXT_PUBLIC_API_URL=${API_ORIGIN:-https://api.mtmux.com} \
    turbo build --filter=@app/web --filter=@app/api
  ```

- **The bundle check.** Between build and staging, `deploy-hosted.mjs` greps
  `apps/web/.next/static/chunks` for the API origin and **refuses to deploy** if
  it is absent. That guard is the point: every one of these failures produces a
  page that loads and looks fine until someone tries to pair.

- **`pnpm prepare:standalone`.** `output: "standalone"` writes a self-contained
  server tree but deliberately omits `.next/static` and `public/`. Without them
  the server boots and answers, and every page loads without its JavaScript or
  assets.

- **The reload.** Rebuilding changes chunk hashes, so a process that is not
  reloaded serves a tree that no longer matches what it hands out.

Verify with `curl -s https://api.mtmux.com/health`.

### Crossing a protocol break

0.7.0 raised the pairing protocol floor, and any future break works the same
way. The order is not interchangeable:

1. **Publish the CLI to npm first.** A new CLI pairs happily with the *old*
   broker — Zod strips the version field it does not know and the socket query
   is ignored — so there is no window where the published CLI cannot work.
2. **Deploy the broker and the web client together.** The browser bundle is
   served by us, so every visitor upgrades on reload as the floor lands.
   Deploying the broker first strands browsers holding the previous bundle.
3. **Existing pairings survive.** Nobody re-pairs.
4. **Tell people to update.** A CLI below the floor keeps its current tunnel
   until its agent socket next reconnects, then reports itself outdated and
   stops retrying rather than looping on a refusal it cannot explain.

Roll back by lowering `API_MIN_PROTOCOL` — the floor is config, so recalling a
floor does not require a deploy.

## Generic PM2

```bash
pnpm build
pm2 start ecosystem.config.cjs
```

Wrapper scripts:

```bash
pnpm start:prod      # pnpm build && pm2 start ecosystem.config.cjs
pnpm logs:prod       # pm2 logs
pnpm restart:prod    # pm2 reload ecosystem.config.cjs
pnpm stop:prod       # pm2 stop ecosystem.config.cjs
```

PM2 ships as a devDependency, so no global install is needed. Logs go to
`logs/<app>-out.log` and `logs/<app>-err.log`.

Cluster mode is what makes `pm2 reload` zero-downtime: PM2 brings up a
replacement worker, waits for it to listen, then retires the old one. Only
`mtmux-app` and `mtmux-web` are in cluster mode, for the reason above.

## Production environment

```bash
# === Relay ===
AUTH_TOKEN=…                            # openssl rand -hex 32
RELAY_HOST=0.0.0.0
RELAY_PORT=24300
ALLOWED_PATHS=/home/deploy
CORS_ORIGINS=https://terminal.example.com

# === Web ===
NEXT_PUBLIC_RELAY_URL=wss://terminal.example.com/ws
NEXT_PUBLIC_API_URL=https://api.example.com

# === Broker ===
API_PORT=24400
API_HOST=127.0.0.1
API_CORS_ORIGINS=https://app.example.com
API_MIN_PROTOCOL=            # empty: the version this build ships with. 0 disables the floor.
API_ADVISORY=                # optional line shown to every CLI that checks in
```

Two startup guards will stop a bad deploy dead:

- The **relay** exits if `AUTH_TOKEN` is empty or the default sentinel
  `change-me-in-production` while bound to a non-loopback address, and if
  `NODE_ENV=production` with a `localhost` origin in `CORS_ORIGINS`.
- The **broker** exits if `NODE_ENV=production` with a `localhost` origin in
  `API_CORS_ORIGINS`.

Both are deliberate. See [Configuration](/docs/configuration).

## Docker

`docker-compose.prod.yml` defines `relay`, `web` and `docs`:

```bash
docker compose -f docker-compose.prod.yml up -d
```

With the bundled nginx sidecar:

```bash
docker compose -f docker-compose.prod.yml --profile nginx up -d
```

The `--profile nginx` switch adds an `nginx:1.27-alpine` container fronting the
three services on ports 80 and 443. Its configs live at `nginx/docker/nginx.conf`
and `nginx/docker/default.conf`.

The relay container needs the host's tmux socket. The compose file mounts
`/tmp/tmux-1000` — adjust it to match your user:

```bash
ls /tmp/tmux-$(id -u)/
```

TLS is bring-your-own-cert. Issue on the host and let the
`./nginx/letsencrypt:/etc/letsencrypt:ro` bind mount expose them:

```bash
sudo certbot certonly --standalone -d your-domain.com
```

There is deliberately no automatic certbot companion — the host's system cron is
simpler to reason about and debug.

## Reverse proxy

### CLI, single port

Proxy everything to one port with WebSocket upgrade headers. Do **not** add a
separate `/ws` location.

```nginx
location / {
    proxy_pass http://127.0.0.1:14100;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 3600s;
}
```

Caddy:

```text
mtmux.example.com {
  reverse_proxy 127.0.0.1:14100
}
```

### Split model

Two ready-to-use configs ship in the repo: `nginx/mtmux.conf.example` for
nginx on the host, and `nginx/docker/default.conf` for the sidecar.

```nginx
server {
    listen 443 ssl;
    server_name terminal.example.com;

    ssl_certificate     /etc/letsencrypt/live/terminal.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/terminal.example.com/privkey.pem;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    client_max_body_size 10M;

    location /ws {
        proxy_pass http://127.0.0.1:14300;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_read_timeout 3600s;
    }

    location / {
        proxy_pass http://127.0.0.1:14100;
        proxy_set_header Host $host;
    }
}
```

### Proxying the broker

The broker needs the same WebSocket upgrade treatment and a **generous read
timeout**, since an idle tunnel holds its socket open for as long as its quota
allows — up to 12 hours by default.

It also needs `X-Forwarded-For` to be correct. Behind a proxy the socket peer is
always loopback, and without the header every rate limit would share a single
bucket. The broker reads only the left-most entry, and only the address.
