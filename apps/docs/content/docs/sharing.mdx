title: Sharing a Session
description: Give someone one tmux session without giving them the machine — and what that does and does not mean.
---

`mtmux share` hands one tmux session to another person. They get a pairing
code, scan or type it, and land in that session. They do not get a shell prompt
of their own, a file browser, or the rest of your machine.

```bash
mtmux share work
```

```
  Sharing 1 session (work) · read-write · no file access · expires in 7 days

  Read-write means they are typing into a shell on this machine. The relay
  keeps them in this session, but the shell does not — they can run
  `tmux switch-client`, read ~/.ssh, or anything your user account can do.
  Use --read-only for a share that is actually a boundary.

  492 716 384
  https://app.mtmux.com/j/492716384

  Waiting for them to join… Ctrl+C stops the share.
```

## Read the paragraph above the code

That warning is not boilerplate, and it is the reason this page exists.

**A read-write share is a scope on the client, not a boundary on the machine.**
mtmux will keep the browser inside the session you named — it refuses every
message that would touch another one, and it refuses file operations you did not
grant. But the person is typing into a shell running as your user. A shell can
do anything your user can do. `tmux switch-client` moves to another session,
`cat ~/.ssh/id_ed25519` reads a key, `curl … | sh` runs whatever it likes.

Read-write sharing is genuinely useful — against mistakes, against a compromised
browser, and for pairing with someone you already trust with the machine. It is
not a way to let a stranger onto a box.

**A read-only share is a real boundary.** The viewer is attached to a locked
copy of the session:

```
tmux new-session -d -t work -s __mtmux_grn_…
tmux set-option -t __mtmux_… prefix None
tmux set-option -t __mtmux_… prefix2 None
tmux set-option -t __mtmux_… key-table mtmux-locked
```

No prefix key, no key bindings, and the relay drops `terminal:input` before it
reaches the PTY. There is nothing to type into. The grouped clone shows the same
windows live, and `prefix` and `key-table` are *session* options, so your own
client is unaffected.

<Callout type="warn">
`tmux attach-session -r` is **not** enough on its own. tmux documents that under
`-r`, keys bound to `detach-client` **and `switch-client`** still work — and `(`
and `)` are bound to `switch-client` by default. A viewer could page through
every session on the machine. The locked clone is what closes that.
</Callout>

```bash
mtmux share work --read-only
```

## Flags

```bash
mtmux share <session> [--read-only] [--files none|ro|rw]
                      [--expires 24h|7d|never] [--label …] [--no-qr]
mtmux share list
mtmux share revoke <grantId>
```

| Flag | Default | Effect |
| --- | --- | --- |
| `--read-only` | off | They watch; input is refused. A real boundary. |
| `--files <level>` | `none` | `none`, `ro` (read), `rw` (read + write). |
| `--expires <duration>` | `7d` | `30m`, `24h`, `7d`, `2w`, or `never`. |
| `--label <text>` | `Share of <session>` | What it is called in `mtmux share list`. |
| `--no-qr` | — | Print the code without the QR block. |
| `-p, --port <n>` | `14100` | The port mtmux is serving on. |

Comma-separate to share several at once: `mtmux share work,logs`.

### Files are off by default

A share with file access turned on uses the *same* allow-list as the machine
itself, which defaults to your entire home directory — and `file:delete` is one
of the operations. That is not a share of one tmux session.

There is no principled setting in between. Deriving an allow-list from the
session's `pane_current_path` looks like a boundary and is not one, because `cd /`
moves it. So the options are off, or the allow-list the machine already has.
Off is the default.

## `mtmux share list`

```
  grn_k4m2p9x7q3v8n5rd  active   work  read-write  files:none
  grn_9f3b2d8a1c6e4570  expired  logs  read-only   files:ro
```

Shares live in `~/.mtmux/grants.json`, mode `0600`. That is a **separate file**
from `config.json` on purpose: grants churn every time you share something, and
a truncated write must not be able to cost you your device identity.

They are also local-only, permanently. Storing them on the broker would hand it
a map of which session names you share with which browsers — exactly the thing
[the broker is built not to know](/docs/sealed-tunnel).

## `mtmux share revoke`

```bash
mtmux share revoke grn_k4m2p9x7q3v8n5rd
```

Takes effect immediately if the server is running, and on the next connection
either way. The file is the record of truth; the running server is told as a
courtesy so you do not have to restart it.

## Sharing from the start

If you want the code `mtmux start` prints to be scoped rather than
full-privilege:

```bash
mtmux start --share work --read-only
```

The device that joins with that code gets the same grant `mtmux share` would
have given it. Devices that paired earlier are unaffected — they keep whatever
they were given.

## What the other person sees

The web client reads its own capabilities from the relay at connect time and is
honest about them:

- a read-only share shows a **Read-only** banner and hides the keyboard toolbar
  and the command bar, instead of accepting keystrokes that vanish;
- a share with `--files none` has no Files tab at all.

None of that is a security control — every restriction is enforced on the
server, for every message, whatever the browser does. It is there so a scoped
share reads as a scoped share rather than as a broken app.

## Session ids, not names

A grant records the tmux `session_id` (`$3`), not the name. Names are mutable —
`tmux rename-session` is one keystroke away — and matching on them would mean a
rename either silently moved your share onto whatever took the old name, or
silently voided it. The first of those is a privilege-escalation primitive.

For the same reason, **`session:rename` is refused for any share narrower than
the whole machine.** Nobody wants "the person I shared one session with can
rename it".

Session ids restart at `$0` when the tmux server itself restarts, so a grant
also records the tmux server pid. If that pid has changed, mtmux re-pins the
grant by name once and logs it. Failing closed would kill every share on reboot,
which is the wrong trade for a tool that runs on servers.

## From the dashboard

The **Share** button on a machine in your dashboard builds the command and
copies it — it does not create the share.

That is deliberate rather than unfinished. Minting a grant needs the tmux truth
about which sessions exist (only the machine has it) and a live socket to the
broker to arm a code (only the running `mtmux` process has one, and in split
mode there is no agent at all). A button that appeared to create a share would
have to reach a machine that might be offline, and would fail in a way that
looks like a bug rather than like the truth.

## Sharing a recording instead

`mtmux share` hands over a live session. If what you want to hand over is what
*already happened*, [`mtmux record share`](/docs/recording) sends a copy of a
`.cast` file instead: the same pairing code and the same sealed tunnel, but the
grant names recordings rather than sessions, so the connection can attach to no
session, send no input and read no files.

It is a firmer boundary than a read-write session share and a weaker one in a
different direction: once the bytes are in someone's browser, revoking does not
take them back.
