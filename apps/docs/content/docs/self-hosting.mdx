title: Self-Hosting
description: Run mtmux entirely on your own infrastructure — including your own pairing broker.
---

mtmux is self-hosted by default. The CLI runs on your machine, talks to your
tmux, and holds its own token. This page covers the three degrees of
independence available to you.

## 1. The CLI is already self-hosted

```bash
npm install -g mtmux
mtmux
```

One process, one port, your machine. No account, no configuration file to write,
nothing to deploy. For a single machine this is the whole answer — see
[Getting started](/docs/getting-started).

## 2. Cutting out the broker entirely

```bash
mtmux start --local
```

Contacts no broker at all. LAN and loopback only, by choice rather than by
accident — which is a different thing from the tunnel merely failing. `mtmux local`
is the same command.

To reach it from outside your network without a broker, put the single port
behind your own reverse proxy with TLS:

```nginx
location / {
    proxy_pass http://127.0.0.1:14100;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 3600s;
}
```

You are now responsible for the certificate and for whatever sits in front of
that port. See [Security](/docs/security).

## 3. Running your own broker

If you want the hosted pairing flow on your own infrastructure, run
`apps/api`. Nothing about it is proprietary and nothing about it can read your
traffic — see [The sealed tunnel](/docs/sealed-tunnel).

### The pairing broker

Build and run it:

```bash
pnpm build --filter=@app/api
API_PORT=14400 API_HOST=127.0.0.1 \
API_CORS_ORIGINS=https://terminal.example.com \
  node apps/api/dist/index.js
```

It needs a reverse proxy that **upgrades WebSockets** and has a **generous read
timeout**, since an idle tunnel holds its socket open for as long as its quota
allows — 12 hours by default. It also needs a correct `X-Forwarded-For`:
behind a proxy the socket peer is always loopback, and without the header every
rate limit would share one bucket.

Full variable list in [Configuration](/docs/configuration#pairing-broker).

Accounts are optional and off by default. **Leaving `DATABASE_URL` unset is a
supported configuration**, not an error — accounts switch off and anonymous
pairing carries on.

### Pointing the CLI at it

Once, and it sticks:

```bash
mtmux config set api https://api.example.com
```

That is stored in `~/.mtmux/config.json` and read by every command. Before it
existed you had to pass the broker on every single invocation, which is not a
self-hosted product so much as a hosted one with a workaround.

The other two forms still win over it, in this order:

```bash
mtmux start --api https://api.example.com          # this command only
MTMUX_API_URL=https://api.example.com mtmux        # this process only
MTMUX_API_URL=https://api.example.com mtmux pair 492716384
```

If your web client is also your own, point the QR and the pairing link at it:

```bash
MTMUX_APP_URL=https://app.example.com mtmux
```

### Pointing the browser at it

The bundled web client reads its broker address from `NEXT_PUBLIC_API_URL`,
which Next inlines **at build time**. Setting it on a running process changes
nothing about the bundle already being served.

To ship a CLI whose bundled client points at your broker, set
`MTMUX_BUILD_API_URL` for the build:

```bash
MTMUX_BUILD_API_URL=https://api.example.com pnpm --filter mtmux build
```

To build the standalone web app for your own hosted deployment:

```bash
NEXT_PUBLIC_API_URL=https://api.example.com \
NEXT_PUBLIC_RELAY_URL= \
  turbo build --filter=@app/web
pnpm prepare:standalone
```

Summary:

| Where the broker URL comes from | When       | Scope                                  |
| ------------------------------- | ---------- | -------------------------------------- |
| `--api <url>`                   | runtime    | one command                            |
| `MTMUX_API_URL`                 | runtime    | the CLI's own requests, this process   |
| `mtmux config set api`          | stored     | the CLI's own requests, this machine   |
| `MTMUX_APP_URL`                 | runtime    | the pairing link and QR the CLI prints |
| `MTMUX_BUILD_API_URL`           | build time | the bundled web client inside the CLI  |
| `NEXT_PUBLIC_API_URL`           | build time | a separately built web app             |

### Accounts on your broker

If you set `DATABASE_URL`, two guards fire in production: the session signing
secret must not be the development sentinel, and `BETTER_AUTH_URL` must be
`https://`, because session cookies are issued `Secure`. See
[Configuration → Hosted accounts](/docs/configuration#hosted-accounts-optional)
and [Accounts](/docs/accounts).

Remember that an account is scoped to the broker that issued it. Signing in to
`api.mtmux.com` gives you nothing on your own broker, deliberately — sending
that token anywhere else would be a credential leak.

## `docker compose up` — the supported path

Your own broker and your own web client, talking to each other and to nothing
of ours:

```bash
git clone https://github.com/mtmux/mtmux.git
cd mtmux
cp .env.example .env
docker compose up
```

That is the whole procedure. It comes up **working with `DATABASE_URL` unset**:
no accounts, no billing, no secrets to manage, anonymous pairing on. That is
the default mode rather than a degraded one — accounts are optional forever.

| Service | Port  | What it is                                                                |
| ------- | ----- | ------------------------------------------------------------------------- |
| `api`   | 24400 | The pairing broker. Blind by construction.                                |
| `web`   | 24100 | The browser client, built against _your_ broker.                          |
| `relay` | 24300 | Opt-in: `docker compose --profile relay up`. The CLI already bundles one. |
| `docs`  | 24102 | Opt-in: `docker compose --profile docs up`.                               |

Two things to change in `.env` before anyone but you can use it:

```bash
NEXT_PUBLIC_API_URL=https://api.example.com   # where browsers reach the broker
API_CORS_ORIGINS=https://app.example.com      # where the client is served from
```

`NEXT_PUBLIC_API_URL` is a **build argument**, not a runtime one — Next inlines
it into the client bundle. Change it and rebuild (`docker compose build web`);
setting it on a running container changes nothing about the bundle already
being served, which is the most confusing failure in this whole page because
the site loads and looks fine until someone tries to pair.

Then point your CLI at it, once:

```bash
mtmux config set api https://api.example.com
```

## The split web + relay model

For containers and multi-tenant deployments the web app and relay run as
separate services. This is the shape `docker-compose.prod.yml` and
`ecosystem.config.cjs` use.

```bash
git clone https://github.com/mtmux/mtmux.git
cd mtmux
cp .env.example .env
```

Set at least:

```bash
AUTH_TOKEN="$(openssl rand -hex 32)"
CORS_ORIGINS="https://terminal.example.com"
NEXT_PUBLIC_RELAY_URL="wss://terminal.example.com/ws"
```

Then either:

```bash
docker compose -f docker-compose.prod.yml up -d
```

or:

```bash
pnpm build
pm2 start ecosystem.config.cjs
```

Full details, including the reverse-proxy configs that ship in `nginx/`, are in
[Deployment](/docs/deployment).

### tmux socket access from a container

The relay container needs the host's tmux socket. The compose file mounts
`/tmp/tmux-1000`; adjust it to match your user:

```bash
ls /tmp/tmux-$(id -u)/
```

### Pre-built images

```bash
docker pull ghcr.io/mtmux/mtmux-api:latest
docker pull ghcr.io/mtmux/mtmux-web:latest
docker pull ghcr.io/mtmux/mtmux-relay:latest
```

The published `web` image is built against `http://localhost:24400`, because an
image cannot know your domain. For any deployment where the browser reaches the
broker at some other address, build it yourself with the argument set — that is
what the compose file above does.

## Checklist

- Generate a real `AUTH_TOKEN` — the relay refuses to boot with the default on a
  non-loopback bind.
- Set `CORS_ORIGINS` to your exact production origin. Production refuses
  `localhost`.
- Narrow `ALLOWED_PATHS`.
- Terminate TLS in front of everything. The sealed tunnel is encrypted
  end-to-end regardless, but the direct path is not.
- Give WebSocket routes a long `proxy_read_timeout`.
- Read [Security](/docs/security).
