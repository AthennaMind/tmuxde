The binary is `mtmux`. `start` is the default command, so bare `mtmux` and
`mtmux start` are the same thing.

```
mtmux [command] [options]
```

`mtmux --help` lists commands; `mtmux <command> --help` lists that command's
flags.

## Commands at a glance

| Command                             | What it does                                                                                                    |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `mtmux`                             | Alias for `mtmux start` — the command you actually use                                                          |
| `mtmux start`                       | Serve this machine's tmux on this network. `--hosted` also opens a sealed tunnel and prints a QR + pairing code |
| `mtmux local`                       | Serve this network only, whatever `reach` is set to                                                             |
| `mtmux pair [code]`                 | The other direction: join a pairing a browser started                                                           |
| `mtmux share <session>`             | Share one tmux session without sharing the machine                                                              |
| `mtmux record <session>`            | Capture a session or pane to a `.cast` on this machine                                                          |
| `mtmux status`                      | Show the server running on this machine                                                                         |
| `mtmux stop`                        | Stop the server running on this machine                                                                         |
| `mtmux doctor`                      | Check everything mtmux needs                                                                                    |
| `mtmux login` / `logout` / `whoami` | Account, which is optional                                                                                      |
| `mtmux servers`                     | List the machines on your account                                                                               |
| `mtmux devices`                     | Browsers this machine trusts                                                                                    |
| `mtmux upgrade`                     | Open checkout for Pro                                                                                           |
| `mtmux token`                       | Manage the auth token                                                                                           |
| `mtmux config`                      | Read and change settings                                                                                        |
| `mtmux version`                     | Print version info (alias: `v`)                                                                                 |

## `mtmux start`

Serves the web client and the relay WebSocket from one process on one port,
opens a reverse tunnel to the pairing broker, re-admits previously paired
devices, and arms a pairing code.

Scanning the QR it prints opens `app.mtmux.com/j` with the code in the URL
fragment and connects with no further input. Typing the code at
`app.mtmux.com` does the same thing. This is the flow — you do not need a second
command in a second terminal.

```bash
mtmux start [options]
```

| Flag                      | Default                              | Description                                                       |
| ------------------------- | ------------------------------------ | ----------------------------------------------------------------- |
| `-p, --port <number>`     | `14100`                              | HTTP + WebSocket port                                             |
| `-h, --host <address>`    | `0.0.0.0` on a LAN, else `127.0.0.1` | Bind address. An explicit value always wins.                      |
| `--local`                 | on unless `reach` says otherwise     | LAN and loopback only — never contact a broker. Beats everything. |
| `--hosted`                | off                                  | Also open a tunnel and print a code for app.mtmux.com             |
| `--no-qr`                 | QR shown                             | Print the code without the QR block                               |
| `-n, --name <label>`      | this machine's hostname              | What to call this machine in the dashboard                        |
| `-t, --token <value>`     | the stored token                     | Override the auth token for this run only                         |
| `--allowed-paths <paths>` | `$HOME`                              | Comma-separated path allow-list for the file browser              |
| `--open`                  | off                                  | Also open a browser on this machine                               |
| `--api <url>`             | `https://api.mtmux.com`              | Pairing service base URL                                          |
| `--json`                  | off                                  | Print a machine-readable startup record instead of the banner     |

### The default bind address

There is deliberately **no fixed default**. `mtmux start` looks for a usable
IPv4 address on a real network interface and binds `0.0.0.0` if it finds one,
`127.0.0.1` if it does not.

"Usable" excludes container bridges, VM host-only networks and overlay VPNs
(`docker*`, `br-*`, `veth*`, `virbr*`, `vmnet*`, `vboxnet*`, `tun*`, `tap*`,
`utun*`, `zt*`, `tailscale*`, `wg*`, `lxcbr*`, `cni*`, `flannel*`, `kube*`), and
accepts only private ranges, preferred in this order: `192.168/16`, then
`10/8`, then `172.16–31`, then `169.254/16` as a last resort. Anything public is
dropped — a public address is not "your network".

Binding the LAN does not open up access. The relay refuses to serve a default or
empty token on a non-loopback bind, and the CLI always holds a 32-byte random
one. Pass `--host 127.0.0.1` if you want loopback only anyway.

### `--json`

```json
{
  "version": "0.6.3",
  "localUrl": "http://localhost:14100",
  "lanUrl": "http://192.168.1.5:14100",
  "mode": "tunnel",
  "code": "492716384",
  "joinUrl": "https://app.mtmux.com/j#492716384",
  "token": "…",
  "note": null
}
```

`mode` is `"tunnel"` or `"local"`. `code` and `joinUrl` are `null` in local
mode. `note` carries a degradation message — for example when the broker could
not be reached and `start` fell back to serving locally.

### When the broker is unreachable

The tunnel is a convenience, not a dependency. An offline machine, a blocked
outbound connection or a broker outage all leave a working LAN server behind,
with the reason printed as a dim note under the addresses. This is what makes
`mtmux start` behave identically to its self-hosted shape when the hosted
service is absent.

### The live panel

On a TTY, `mtmux start` keeps a panel at the bottom of the screen showing every
device this machine trusts — connected ones first, then the ones that are
paired but not here, dim, with when each was last seen. Everything the command
prints scrolls above it, so the panel is never left stranded in the scrollback.
It is absent off a TTY — a pipe, a service unit, `--json`, or a terminal under
twelve rows — where the output stays a plain append-only log.

Listing the absent ones is not cosmetic. The most common thing anyone wants to
do to a device is get rid of one that is _not_ here — a phone you lent out, a
laptop you sold — and until they were on this list that meant quitting the
server and running `mtmux devices revoke <id>` with an id you had to go and
find.

| Key     | What it does                                                |
| ------- | ----------------------------------------------------------- |
| `↑` `↓` | Move between devices                                        |
| `d`     | Everything about this device. `enter` does it too           |
| `r`     | Remove it. It must pair again, with a new code and approval |
| `e`     | Rename it, so the list reads as yours                       |
| `a`     | Ask again when a device you know comes back                 |
| `t`     | Open the encrypted tunnel, on a server started local-only   |
| `n`     | Throw away the printed code and arm a fresh one             |
| `l`     | Reprint the banner, code and addresses                      |
| `?`     | These keys                                                  |
| `q`     | Stop the server, the same as `Ctrl+C`                       |

The bar along the bottom carries five of these and `?` carries the rest. A row
of seven key-and-word pairs is a row nobody reads, and `t` in particular is
offered as a whole sentence above the bar rather than as two more characters
inside it.

**`e` renames.** Three rows all reading "Chrome on macOS" is a list you cannot
act on. A name is yours, changes nothing about what the device may do, and never
overwrites what the browser claimed to be — the detail card shows both when they
differ, because that is the one field that can contradict a name. `mtmux devices
rename` does the same thing on a machine with no panel.

**`a` flips whether a device you already trust is asked about when it returns.**
That setting is behind nearly every report of "it let something in without
asking me": it _had_ asked, once, when that device first paired. A new device is
always asked about, either way. The banner names the trusted count and says
which way this is set, because a setting nobody can see is one nobody can be
wrong about.

`t` and `n` are never both offered: `t` opens the tunnel a machine does not
have, `n` replaces a code it already printed. A key that cannot work is worse
than a key that is absent.

**`r` removes, and there is no second, softer key beside it.** There used to be:
`c` hung up the socket and left the credential alone, sold as the reversible
one. It was reversible in the worst way — the device still held a working token
and was back within the second, so the list looked untouched and the panel
looked broken. Getting rid of a device now means forgetting it: the token is
revoked, its socket closes, its keys leave the tunnel agent's ring, and coming
back costs a new code and a fresh approval. The confirmation says exactly that
before anything happens.

`c` still lands on the same question, because it is the key people learned, and
arriving at a confirmation is not the same as arriving at a consequence. A
connection with no pairing record behind it — a browser using this machine's own
token, or a share — has no credential of ours to destroy, so there `r` offers to
hang up instead and says outright that it can come straight back.

`d` opens a card for the selected connection: what it is attached to, the
viewer's screen size, what the grant allows in a sentence, how it reached this
machine — "through the encrypted tunnel", "over this network", "from this
machine" — and the device id in full, because that is what `mtmux devices
revoke` takes. A connection with no pairing record is named from its user agent
("Safari on iPhone") rather than left as a third row called "A device".

When a device asks for access, the question is drawn in this panel and answered
with `y`/`n` from the same key reader. There is exactly one reader on stdin at
any time; a `[y/N]` prompt that keeps eating keystrokes after the question has
been answered on a phone is a bug this shape makes impossible.

## `mtmux local`

```bash
mtmux local [options]
```

Alias for `mtmux start --local`. It accepts `-p/--port`, `-h/--host`,
`--no-qr`, `-t/--token`, `--allowed-paths`, `--open` and `--json`. It does
not accept `--name` or `--api`, since neither means anything without a broker.

In local mode the QR encodes a LAN sign-in URL — `http://<lan>:<port>/login#n=<nonce>`
— instead of a pairing code.

## `mtmux pair`

The **other** direction. `mtmux start` prints a code for a browser to claim;
`mtmux pair` claims a code a browser is already showing. Open
`https://app.mtmux.com/pair` on the device, read the code, and quote it
here.

```bash
mtmux pair 492716384
```

Run with no code and it prints those steps rather than guessing.

Reach for it when you are already at the browser, when you are pairing a machine
you got to over SSH, or when you want `--tunnel-only`. For the ordinary case,
`mtmux` and a scan is fewer moving parts.

| Flag                  | Default                 | Description                                                    |
| --------------------- | ----------------------- | -------------------------------------------------------------- |
| `-p, --port <number>` | `14100`                 | Port mtmux is already serving on                               |
| `--api <url>`         | `https://api.mtmux.com` | Pairing service base URL                                       |
| `--tunnel-only`       | off                     | Advertise no direct addresses; always relay through the tunnel |

`mtmux pair` requires a server to already be running on that port — it checks
`http://127.0.0.1:<port>/health` first and refuses with a pointer to
`mtmux start` if nothing answers.

It stays in the foreground holding the tunnel open. Ctrl+C ends remote access;
the local and LAN paths are unaffected.

## `mtmux share`

Share one tmux session with someone, without sharing the machine. Full details,
including what a read-write share does and does not protect, are in
[Sharing a Session](/docs/sharing) — read that page before you use this.

```bash
mtmux share <session>            # comma-separate for several
mtmux share list
mtmux share revoke <grantId>
```

| Flag                   | Default                 | Effect                                       |
| ---------------------- | ----------------------- | -------------------------------------------- |
| `--read-only`          | off                     | They watch and cannot type. A real boundary. |
| `--files <level>`      | `none`                  | `none`, `ro`, `rw`                           |
| `--expires <duration>` | `7d`                    | `30m`, `24h`, `7d`, `2w`, `never`            |
| `--label <text>`       | `Share of <session>`    | Name in `mtmux share list`                   |
| `--no-qr`              | —                       | Print the code without the QR block          |
| `-p, --port <number>`  | `14100`                 | Port mtmux is serving on                     |
| `--api <url>`          | `https://api.mtmux.com` | Pairing service base URL                     |

Requires a server already running on that port — the grant is pinned to tmux
session ids, and only the running relay knows them.

`mtmux start --share <sessions> [--read-only] [--files …]` does the same thing
to the code `start` itself prints, so the first device to join is scoped rather
than full-privilege.

## `mtmux record`

Capture a tmux session or one pane to a file under `~/.mtmux/recordings/`. What
a recording contains, and what sharing one does and does not mean, are in
[Recording a Session](/docs/recording) — read that page before you share one.

```bash
mtmux record <session>
mtmux record list
mtmux record stop <id>
mtmux record rm <id>
mtmux record share <id>
```

| Flag                   | Applies to     | Default              | Effect                                                 |
| ---------------------- | -------------- | -------------------- | ------------------------------------------------------ |
| `--pane <id>`          | `record`       | —                    | Record one pane (a tmux `%id`) instead of the session  |
| `--title <text>`       | `record`       | the session name     | What the recording is called, in the file's own header |
| `--json`               | `record list`  | —                    | Print one JSON document and nothing else               |
| `--all`                | `record stop`  | —                    | Stop every recording                                   |
| `--expires <duration>` | `record share` | `7d`                 | `30m`, `24h`, `7d`, `2w`, `never`                      |
| `--label <text>`       | `record share` | `Recording: <title>` | Name in `mtmux share list`                             |
| `--no-qr`              | `record share` | —                    | Print the code without the QR block                    |
| `-p, --port <number>`  | all            | `14100`              | Port mtmux is serving on                               |

Requires a server already running on that port: only the running process holds
the tmux connection the recorder attaches through.

There is deliberately no `mtmux start --record`. Recording is something you
start when the thing worth recording is about to happen, not a mode you boot
into.

## `mtmux status`

```
  Status   running  pid 48213
  Uptime   2h 14m
  Mode     tunnel + local
  Local    http://localhost:14100
  Network  http://192.168.1.5:14100
  Invite   https://app.mtmux.com/j#492716384
  Devices  2  iPhone · Safari, MacBook · Chrome
  Version  0.6.3
```

`Devices` lists what is connected **right now**, which is not the same as what
is paired — `mtmux devices` answers that. The row is omitted entirely by a
server too old to report it.

Read from `~/.mtmux/server.json`. That file is a hint, not a lock: every read
checks the pid is still alive and the port still answers `/health`, and a record
that fails is deleted rather than reported.

## `mtmux stop`

Sends `SIGTERM` to the recorded pid and waits up to 8 seconds for it to go, then
escalates to `SIGKILL`. `SIGTERM` first because the server has a shutdown path
that closes the tunnel cleanly. If the process belongs to another user, it
reports that rather than pretending to have stopped it.

## `mtmux doctor`

```bash
mtmux doctor [-p <port>] [--api <url>]
```

Six checks in dependency order, so the first failure is the cause rather than a
symptom. Exits `1` if anything fails; warnings alone exit `0`. See
[Troubleshooting with doctor](/docs/doctor).

## `mtmux devices`

Browsers this machine has paired with. These are **local** records, kept in
`~/.mtmux/config.json` — the command works with no account and no network.

```bash
mtmux devices                    # list (the default subcommand)
mtmux devices list
mtmux devices rename <deviceId> [name...]
mtmux devices revoke <deviceId>
```

`rename` with no name clears it back to whatever the browser calls itself. It
changes nothing about what that device may do — it exists so the list reads as
yours rather than as three rows of user-agent strings.

Paired devices survive a restart: `mtmux start` restores both halves of what it
derived with each one — the relay token for the direct/LAN path and the key
schedule the sealed tunnel needs — so a browser stays trusted until it is
revoked or goes stale.

Before 0.6.2 only the relay token was restored. A device paired by an older
version therefore reconnects on the local network but not through the tunnel.
`mtmux start` says so on startup, and pairing it once more fixes it permanently.

A device idle for more than 90 days is shown as `(stale)` and is not re-admitted
on the next start. Revoking drops the record immediately, so the device can
never reconnect — but a browser holding a live socket keeps it until the server
restarts. The command says so.

## `mtmux config`

```bash
mtmux config get                              # every setting
mtmux config get reconnectPolicy
mtmux config set reconnectPolicy confirm
mtmux config set reach hosted                 # tunnel by default on this box
mtmux config set api https://api.example.com  # your own broker
mtmux config set api default                  # back to ours
```

Three settings, deliberately. Everything else this CLI does is either a per-run
flag or a decision the product should make for you.

**`reach`** — how far `mtmux start` goes when nobody says.

| Value             | Meaning                                                       |
| ----------------- | ------------------------------------------------------------- |
| `local` (default) | Serve the LAN and loopback. Contact nothing.                  |
| `hosted`          | Also open a sealed tunnel and print a code for app.mtmux.com. |

`--local` and `--hosted` both beat this for one run, and `--local` beats
`--hosted` — an explicit "not now" should win over a preference set weeks ago.
This default used to be `hosted`. Reaching the internet is the more useful
behaviour _and_ the one with consequences, and a default is whatever happens to
someone who typed the shortest command in the product without reading what it
did.

**`reconnectPolicy`** — whether a device paired in an earlier run may reconnect
without being asked.

| Value             | Meaning                                                                                                                   |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `trust` (default) | Paired means paired, the way a Bluetooth keyboard is paired. A machine under systemd survives a reboot with nobody at it. |
| `confirm`         | A returning device raises a prompt on this machine the first time it reconnects after a restart.                          |

Under `confirm` the prompt shows no comparison code, because there is nothing to
compare: the device already proved itself cryptographically — its key schedule
is what decrypted the frame. The question is policy, not verification.

With no TTY, `confirm` **refuses**. Admitting a device because nobody could be
asked would be the setting quietly not applying.

**`api`** — the pairing broker this machine uses. Set it once instead of
exporting `MTMUX_API_URL` or passing `--api` on every invocation. Precedence,
highest first:

1. `--api <url>`
2. `MTMUX_API_URL`
3. `mtmux config set api`
4. the broker this machine's account signed in against
5. `https://api.mtmux.com`

`default` (or an empty value) clears it. Only absolute `http(s)` URLs are
accepted — `http` on purpose, because a self-hosted broker's first home is
usually the local network.

Override per run with `--confirm-reconnect` or `--trust-reconnect`; the flags
beat the stored value, and `--trust-reconnect` wins if both are passed.

Changes take effect the next time `mtmux start` runs.

## `mtmux token`

```bash
mtmux token print          # show the current token
mtmux token rotate         # generate a new 32-byte random token
mtmux token set <value>    # set a specific value
```

`rotate` preserves the device key and every paired peer. Rotating a token should
not un-pair every device you own.

## Account commands

All optional. See [Accounts](/docs/accounts).

| Command         | Description                                                      |
| --------------- | ---------------------------------------------------------------- |
| `mtmux login`   | Sign in via OAuth device authorization — works on a headless box |
| `mtmux logout`  | Sign out on this machine                                         |
| `mtmux whoami`  | Show the signed-in account, plan and broker                      |
| `mtmux servers` | List the machines registered to the account                      |
| `mtmux upgrade` | Open checkout for mtmux Pro                                      |

`login`, `logout`, `whoami`, `servers` and `upgrade` all take `--api <url>`.
`login` and `upgrade` also take `--no-open`.

An account is stored against the broker that issued it. Point the CLI at a
different `--api` and you are anonymous there until you sign in again — a token
minted by `api.mtmux.com` means nothing to a self-hosted broker, and sending it
anyway would be a credential leak.

## Environment variables

| Variable              | Effect                                                                                                                                   |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `MTMUX_CONFIG_DIR`    | Directory holding `config.json` and `server.json`. Default `~/.mtmux`.                                                                   |
| `MTMUX_API_URL`       | Pairing broker base URL. Default `https://api.mtmux.com`. `--api` overrides it.                                                          |
| `MTMUX_APP_URL`       | Web client origin used to build the pairing link and QR. Default `https://app.mtmux.com`. Point it at your own deployment of `apps/web`. |
| `MTMUX_BUILD_API_URL` | **Build time only.** Bakes a broker origin into the bundled web client.                                                                  |

## Files

| Path                        | Contents                                                                                                                               |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `~/.mtmux/config.json`      | Auth token, device key, paired peers, account, server name. Mode `0600`.                                                               |
| `~/.mtmux/grants.json`      | Shares created with `mtmux share`. Mode `0600`. Separate from `config.json` so a truncated write cannot cost you your device identity. |
| `~/.mtmux/recordings/`      | `.cast` files from `mtmux record`, plus an `index.json`. Directory `0700`, files `0600`.                                               |
| `~/.mtmux/server.json`      | The running server's pid, port, URLs and mode.                                                                                         |
| `~/.tmuxremote/config.json` | Legacy location. Its token is adopted on first run if the new file is missing.                                                         |

## Commands that do not exist

If you have seen these in an older guide or a generated snippet, they are not
part of mtmux and never were: `mtmux up`, `mtmux down`, `mtmux watch`,
`mtmux run`, `mtmux notify`, `mtmux sessions`. There is likewise no
`~/.mtmux/agents.toml` — configuration is `config.json`, and shares are
`grants.json`.
