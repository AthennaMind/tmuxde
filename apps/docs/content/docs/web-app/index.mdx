The web client (`apps/web`) is the Next.js application `mtmux` bundles and
serves. It talks to the relay over the typed WebSocket protocol in
`@repo/protocol`.

## What it does

- **A real terminal.** xterm.js with optional WebGL rendering, search, Unicode
  11 and clickable links.
- **Sessions.** Create, attach, rename, kill; windows and panes with splits,
  zoom, resize, swap and layouts.
- **Files.** Browse, upload by drag-and-drop, edit in Monaco, preview images,
  video, audio and PDFs.
- **Mobile.** Tab navigation, a keyboard toolbar, swipe and pinch gestures, a
  tmux control sheet, haptics.
- **Customisable.** Terminal themes, font size, cursor, scrollback, which
  toolbar keys appear, which gestures are active.
- **Resilient.** Exponential reconnect with zombie-socket detection, and a
  queue that deliberately drops stale input rather than replaying it into a
  reconnected session.

## Pages

| Route          | Purpose                                                                    |
| -------------- | -------------------------------------------------------------------------- |
| `/`            | The terminal — sidebar, terminal, file panel                               |
| `/[sessionId]` | Deep link to a session; sets it active and restores it later               |
| `/j`           | **The QR target for `mtmux start`.** Claims a code the terminal is showing |
| `/pair`        | The other direction: shows a code for `mtmux pair` to claim                |
| `/login`       | Paste a token, or auto-authenticate from a URL fragment                    |
| `/settings`    | Settings, and the only place with a logout button                          |

`/j` reads the code from the fragment (`/j#49271638`) and pairs with **zero
taps**; with no fragment it falls back to a code field for someone typing
the code by hand.

`/j` and `/login` both strip the fragment with `history.replaceState` before
doing anything else, so the credential is never sent to a server and does not
survive in the address bar or in history. `/login` accepts `#token=…` and
`#n=…`.

## How it connects

Three ways, chosen at runtime in this order:

1. **A paired session with a winning direct candidate** — a plain WebSocket to
   `ws(s)://<candidate>/_relay`.
2. **A paired session with no winner** — a sealed transport over
   `ws(s)://<broker>/v1/tunnel/<tunnelId>`.
3. **Neither** — `NEXT_PUBLIC_RELAY_URL` in a split deployment, or same-origin
   `/_relay` in CLI single-port mode.

Candidates are raced in parallel and one wins only by completing the relay's
auth handshake — not by answering an HTTP probe, which a captive portal can
fake. The timeout is 800 ms. See [How pairing works](/docs/pairing).

Where credentials live: pairing keys **and** the sealed descriptor in IndexedDB,
keyed by the paired machine's device id, with a `sessionStorage` mirror so the
first render can resolve a URL without awaiting a database. Never
`localStorage`, which an XSS can read in one line. The self-hosted token is the
exception — it is in `localStorage`, because there is no pairing to hang it off.

Because the descriptor is durable, **reloading the page does not force a
re-pair**. It used to live in `sessionStorage` alone, so a refresh threw away
the descriptor while the keys survived.

## Reconnection

`RelayClient` re-authenticates on open, backs off exponentially from 1 s to
30 s, pings every 10 s, and drops a socket that has not ponged in 25 s.

Messages queued while disconnected are capped at 50, and several types are
**deliberately dropped** rather than queued: `terminal:input`,
`terminal:resize`, `command:send`, `tmux:prefix`, `session:attach` and
`session:detach`. Replaying keystrokes into a session that has moved on is worse
than losing them.

## Tech stack

- Next.js **16** (App Router), React 19
- Tailwind CSS 4 and shadcn/ui via `@repo/ui`
- Zustand for state, several stores persisted to `localStorage`
- xterm.js for terminal rendering, Monaco (bundled locally, not from a CDN) for
  the editor
- `@repo/crypto` for the sealed transport
