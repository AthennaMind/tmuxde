"Approval" means two unrelated things around an agent session, and confusing
them wastes an afternoon. This page separates them.

|                             | Who asks                                      | Who answers                                                                              | Where                  |
| --------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------- | ---------------------- |
| **Agent permission prompt** | The agent, inside its pane                    | You, by typing into the terminal                                                         | Any paired device      |
| **mtmux access request**    | A browser asking to join a registered machine | A human — in the app on an already-paired device, at the machine, or via `mtmux approve` | Wherever that human is |

## 1. The agent's permission prompt

This is ordinary terminal input. Claude Code's tool-permission prompt and Codex
CLI's `y`/`n`/`a` approval are both just a program blocking on stdin, and a
paired browser is a terminal — so answering from a phone needs nothing beyond
being paired.

What makes it practical on a phone rather than merely possible:

| Problem on a phone                           | What the client does                                                                            |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| The prompt scrolled off                      | Copy mode captures the pane read-only, with Copy All                                            |
| One-character answers are easy to fat-finger | The keyboard toolbar puts them on real buttons; `Ctrl` and `Alt` are sticky rather than chorded |
| A longer correction fights autocorrect       | The command bar is a text area — `Enter` sends, `Shift+Enter` newlines                          |
| It went wrong and must stop now              | `^C` is a fixed toolbar button                                                                  |

Full control reference in [Mobile](/docs/web-app/mobile).

<Callout type="warn" title="A read-only share cannot answer a prompt">
  `mtmux share --read-only` is a real boundary: that device can watch and cannot
  type, so it cannot approve anything. If you are handing a session to someone
  so they can unblock an agent, share it read-write and understand what that
  means — see [Sharing a session](/docs/sharing).
</Callout>

**Nothing announces this state.** No layer of mtmux notices that an agent is
blocked, and mtmux sends no notifications at all. Codex CLI's `notify` hook does
not fire on its approval prompt either. See
[Notifications](/docs/agents/notifications) for what can.

## 2. mtmux's own access request

Separate mechanism, separate purpose. When a browser asks to join a machine
registered to your account, a human is asked to compare six digits and say yes
or no. Consent is a human's, by design — never a timeout's.

There are three places that question can be answered, and they are asked **at
the same time**. Whoever answers first decides.

### In the app

Any device already paired with that machine — your phone, in your hand — gets a
prompt showing the device asking, the account it belongs to, and the six digits
to compare against what that browser is showing on its own screen. Approve or
Deny, one tap.

This is usually the right one, because the premise of mtmux is that you are not
at the machine. It cannot be dismissed by tapping outside it or pressing Escape:
those look like refusing and refuse nothing, and the request would quietly
expire while you believed you had answered. Deny is one tap and it is the
default focus.

A **read-only or single-session share cannot answer**, and is never shown the
question. Admitting a device grants more than such a share holds.

### At the machine

If `mtmux start` is running attached to a terminal, the same comparison appears
there and you press `y` or `n`. Answering in the app closes this prompt, and
vice versa.

### From another shell

On a box nobody is sitting at — systemd, `nohup`, a detached pane — the terminal
prompt finds no TTY and cannot ask. `mtmux approve` is the way in:

```bash
mtmux approve                 # stay available for 5 minutes
mtmux approve -t 15           # …for 15 minutes
mtmux approve --keep          # stay open after the first decision
mtmux approve -p 14100        # a specific server; default is whichever is running
```

<Steps>
  <Step title="Reach the machine however you normally would">
    SSH in. The machine must already be running `mtmux` — `approve` talks to
    that process over loopback, it does not start a server or open a tunnel of
    its own.
  </Step>
  <Step title="Open the window">
    Run `mtmux approve`. For the next few minutes an incoming request is shown
    here instead of being denied.
  </Step>
  <Step title="Trigger the request from the browser">
    Press the join button in the dashboard. The comparison code appears in your
    SSH session — and simultaneously on any device already paired with that
    machine.
  </Step>
  <Step title="Compare the digits, then decide">
    They must match what the browser shows. Matching digits are the whole
    security property; approving without comparing them approves whoever is
    asking.
  </Step>
</Steps>

<Callout type="warn" title="Nobody answering is a no">
  On every channel, in every combination, an unanswered request is denied when
  it expires. Closing the app, walking away from the terminal, or letting the
  approval window lapse are all the same answer: no. Nothing is ever admitted
  because a human failed to object.
</Callout>

<Callout type="info" title="Why there is no approval queue">
  The browser's half of the exchange is an ephemeral key held in one tab's
  memory, with a two-minute lifetime at the broker. There is nothing durable to
  queue: the **window** persists, the **request** cannot. So open the window
  first, then press the button — not the other way round.
</Callout>

Requests only exist for machines registered to an account, but since 0.7.1
**anonymous nine-digit pairing is gated too**. The code used to be treated as
the consent; it is not, because it is read off one screen and typed into
another, so what it proves is that somebody saw the screen. That path now asks
through these same channels, with one difference: there are no digits to
compare, since the code itself was the shared secret. See
[How pairing works](/docs/pairing) and [Accounts](/docs/accounts).

## Revoking

```bash
mtmux devices list
mtmux devices revoke <deviceId>
```

A device stays trusted until it goes 90 days unseen or you revoke it. Rotating
the auth token deliberately does **not** un-pair devices; see
[Security](/docs/security).
