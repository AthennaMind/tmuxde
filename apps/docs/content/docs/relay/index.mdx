title: Relay Server
description: The WebSocket server that bridges browsers to tmux.

The relay (`apps/relay`) is the Node.js server that bridges a browser connection
to tmux on the host machine. It handles authentication, message routing, PTY
management and file operations.

In the CLI it runs **inside** the `mtmux` process and attaches its WebSocket
handler at `/_relay` on the same port as the web client. In the split model it
is a standalone service on port `14300`.

## Startup

1. Parse and validate the environment with Zod. A bad value stops the process.
2. Refuse to boot if the auth token is the default or empty **and** the bind
   address is not loopback.
3. Refuse to boot if `NODE_ENV=production` and `CORS_ORIGINS` contains a
   `localhost` origin.
4. Create the HTTP server and attach the WebSocket upgrade handler.
5. Start the session monitor that watches for session exits.
6. Listen.

## HTTP endpoints

| Endpoint | Method | Auth | Purpose |
| --- | --- | --- | --- |
| `/health` | GET | none | Liveness. Returns `{ status, uptime }`. |
| `/_pair/local` | POST | a pairing nonce in the body | Redeem a LAN sign-in nonce for a session token |
| `/_pair/session` | POST | loopback + `Bearer AUTH_TOKEN` | Register a PAKE-derived session token |
| `/file?path=…` | GET | `Bearer`, or legacy `?token=` | Download or stream a file |
| `/_relay` | WS | `auth` as the first message | The protocol socket |

`GET /_pair/local` is refused with `405` on purpose — a `GET` would put the
nonce in access logs and `Referer` headers.

`/file` supports `?download=1` with a sanitised `Content-Disposition`, and HTTP
Range requests with `206` and `416` responses. That is how the web client streams
images, video and audio — and why those need the direct path rather than the
tunnel, which carries only sealed WebSocket frames.

## Authentication

The **first** message on the socket must be:

```json
{ "type": "auth", "token": "…" }
```

within 5 seconds. Either the long-lived `AUTH_TOKEN` or a live session token is
accepted, compared by SHA-256 digest and `timingSafeEqual`. Success sends
`auth:success` plus a `server:info` frame; failure sends `auth:failure` and
closes the socket.

The relay keeps session tokens in memory only, so a restart clears them. The CLI
compensates: `mtmux start` replays the token it derived with each paired device
through `POST /_pair/session` on boot, so a paired browser stays trusted across
restarts. LAN-nonce sign-ins have no such record and do not survive.

A repeated `auth` frame after authentication is tolerated and re-acknowledged.
That is deliberate: on the tunnel path the agent authenticates the loopback
socket first, and the browser's own `auth` frame arrives second.

Failed attempts are throttled per address — see
[Security](/docs/security#failed-auth-throttling).

## Message routing

After authentication every message goes through `message-router.ts`, one case
per `ClientMessage` type:

- **Sessions** — list, create, attach, detach, kill, rename, windows
- **Terminal I/O** — input, resize
- **Panes and windows** — list, split, select, zoom, resize, swap, kill, layout,
  rotate, capture
- **tmux control** — prefix, copy mode
- **Commands** — send, interrupt, EOF, clear, suspend
- **Files** — list, read, stat, write, create, mkdir, delete, rename, upload,
  watch, unwatch

There is no per-message authorization beyond the connection's authenticated
flag. Anything that can authenticate can do anything the protocol offers.

## Limits

| Limit | Default | Behaviour on exceeding |
| --- | --- | --- |
| Messages per second per connection | `WS_RATE_LIMIT`, 100 | The message is dropped with a `RATE_LIMITED` error. No disconnect. |
| Idle time | `IDLE_TIMEOUT_MINUTES`, 30 | Closed with code 1000, "Idle timeout". `0` disables it. |
| Concurrent connections | 100 total, 10 per address | Upgrade closed with code 1013. |
| WebSocket frame | 1 MiB | Rejected before it reaches a handler. |

The rate limit is checked before parsing and before auth. The idle clock is
updated by any inbound message, including rejected ones. Separately, the relay
pings every 30 seconds after auth and terminates a peer that missed the previous
pong.

## PTY bridge

On `session:attach` the relay spawns a PTY attached to that tmux session. Output
flows PTY → WebSocket as `terminal:output`; input flows the other way as
`terminal:input`. `terminal:resize` propagates size changes to the PTY.

## File service

Every operation calls the path guard first. It resolves symlinks on both the
target and each allowed root before comparing, so a symlink out of an allowed
directory does not escape it. Deleting an allowed root is refused outright.

Fixed caps: 100 KB truncating read, 1 MB write, 10 MB upload. Partial uploads
are unlinked on oversize and on disconnect.

Directory watching uses chokidar at `depth: 0` — the current directory only, not
its subtrees.

## Shutdown

`SIGTERM` and `SIGINT` stop the session monitor, then the WebSocket server, then
the HTTP server.
