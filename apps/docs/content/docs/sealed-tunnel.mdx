When a paired device cannot reach your machine directly, its session rides a
reverse tunnel through `api.mtmux.com`. The broker forwards ciphertext and holds
no key that could open it.

Everything on this page corresponds to code in `packages/crypto/src/`. Nothing
here is aspirational.

<Callout type="warn" title="Status">
  The CPace implementation is checked against the published draft test vectors,
  which proves the encoding and group maths. It has not yet had an independent
  security review of the surrounding protocol wiring. The file says so at the
  top, and so do we.
</Callout>

## The shape of it

```
   Browser                    api.mtmux.com                   Your machine
  ┌─────────┐                ┌──────────────┐               ┌──────────────┐
  │ Sealed  │  stream:frame  │              │ stream:frame  │ Tunnel agent │
  │transport│ ─────────────► │  blind relay │ ────────────► │  (in mtmux)  │
  │         │ ◄───────────── │              │ ◄──────────── │              │
  └─────────┘   ciphertext   └──────────────┘   ciphertext  └──────┬───────┘
                                    ▲                              │ plaintext
                             holds no key                          │ loopback
                                                              ┌────▼────┐
                                                              │  relay  │→ tmux
                                                              └─────────┘
```

The agent is the cryptographic peer, not the relay. Ciphertext in from the
broker, plaintext JSON out to `ws://127.0.0.1:<port>/_relay`, and the reverse
coming back. The relay sees an ordinary authenticated local client and knows
nothing about tunnels, brokers, pairing or AES — which is what keeps the
self-hosted path off the tunnel's critical code.

It also means the machine's 64-hex `AUTH_TOKEN` is injected on _this_ side of
the tunnel and never travels over it.

## Step 1 — CPace

**Ciphersuite: `CPACE-RISTR255-SHA512`**, implementing
[draft-irtf-cfrg-cpace-13](https://datatracker.ietf.org/doc/draft-irtf-cfrg-cpace/)
over `@noble/curves`' audited ristretto255.

CPace is a balanced PAKE: both sides hold the same low-entropy password and end
up with the same high-entropy key, while an observer learns neither.

| Input                     | Value                                      |
| ------------------------- | ------------------------------------------ |
| `PRS` (password)          | The six-digit secret from the pairing code |
| `CI` (channel identifier) | The three-digit slot                       |
| `sid` (session id)        | 16 bytes, chosen by the claimant           |

The run is:

1. **Generator.** `generator_string(DSI, PRS, CI, sid)` is length-value
   concatenated with zero padding sized so the password lands outside the first
   SHA-512 input block — a side-channel on the compression function then cannot
   see password-dependent data in a block whose other inputs are attacker-known.
   That string is hashed with SHA-512 and mapped to the curve with ristretto255's
   one-way map from 64 uniform bytes.
2. **Shares.** Each side samples a scalar — 32 random bytes with the bits above
   252 cleared, read little-endian, so every value is below the group order and
   no reduction and no bias is introduced — and sends `scalar × generator` as a
   32-byte encoding.
3. **Verification.** `scalar_mult_vfy` decodes the peer's share, refuses
   anything that is not a valid ristretto255 element, and **aborts on the
   identity**. Ristretto255 has no small-order elements by construction, so the
   identity is the only degenerate case left — but it is a real one.
4. **ISK.** `SHA-512(lv_cat(DSI_ISK, sid, K) ‖ transcript_ir(Ya, ADa, Yb, ADb))`.
   The transcript is ordered initiator-first, and both sides must agree on which
   they are.

The broker sees the two 32-byte shares and the associated data. From those the
six-digit secret cannot be recovered.

<Callout type="info" title="Why implement it rather than depend on one">
  Every CPace package on npm is pre-1.0 and unaudited, so depending on one would
  move the trust rather than reduce it. `cpace.test.ts` checks every
  intermediate against the draft's Appendix B.3 vectors, which is the only
  reason to trust the file.
</Callout>

## Step 2 — the key schedule

Four keys are derived from the ISK with **HKDF-SHA-256**, salted by the CPace
transcript, one label per purpose, 32 bytes each:

| Label                   | Key                                          |
| ----------------------- | -------------------------------------------- |
| `mtmux/v1 browser→cli`  | AES-256-GCM key for browser → CLI frames     |
| `mtmux/v1 cli→browser`  | AES-256-GCM key for CLI → browser frames     |
| `mtmux/v1 confirm`      | HMAC key for key confirmation                |
| `mtmux/v1 direct-token` | Relay auth token for the direct path, as hex |

Separate labels mean a leak of one key gives an attacker none of the others. The
two directions use **different keys**, so a captured frame can never be
reflected back at its sender.

The direct token is what lets a browser that wins the candidate race
authenticate to the relay without the long-lived `AUTH_TOKEN` ever crossing the
wire: both sides compute it independently from the pairing key.

## Step 3 — key confirmation

Each side sends `HMAC-SHA-256(confirmKey, "mtmux/v1 confirm " + role)` where
role is `cli` or `browser`, and verifies the other's with a constant-time
compare.

This is what turns a wrong six-digit guess into an immediate, visible failure
rather than a silently broken session — and what lets the broker destroy the
mailbox on a bad guess, so an attacker gets exactly one shot.

## Step 4 — sealed frames

Every relay protocol line is sealed with **AES-256-GCM** before it goes near the
broker.

```
first frame of a direction on a stream (counter is always 0):
    [ 16-byte salt ][ 8-byte BE counter ][ ciphertext ‖ 16-byte GCM tag ]
every frame after it:
    [ 8-byte BE counter ][ ciphertext ‖ 16-byte GCM tag ]

nonce (12B):  [ 4-byte direction tag ][ 8-byte BE counter ]
```

- **Salt** is 16 random bytes, generated per connection and carried in the clear
  on the first frame each direction sends. The key that actually seals a frame
  is `HKDF-SHA-256(sessionKey, salt, label)` — a **per-connection subkey**,
  under a label that also separates frames from the sealed descriptor.

  This is the fix for a real bug rather than a precaution. Before 0.7.0 both the
  descriptor and the first frame of a stream were sealed under the same
  direction key at counter 0, which is AES-GCM nonce reuse: XOR of the two
  ciphertexts recovers plaintext, and the forbidden-attack recovers the GHASH
  subkey and with it the ability to _forge_. Every hosted pairing handed the
  broker that pair. A per-connection subkey means no key is ever used twice at
  counter 0, and it makes a reconnect a fresh key schedule rather than a reset
  replay window.

  The salt rides inside the sealed blob, not beside it, for two reasons: it is
  the only field the broker forwards verbatim, and a broker that minted the salt
  would be back inside the key schedule. In the clear, it also keeps trial
  decryption working, which is what lets the broker stay blind.

- **Direction tag** is `"c2s\0"` or `"s2c\0"`. The two directions already use
  separate keys; the tag means they can never collide even so.
- **Counter** must strictly increase. A frame whose counter is less than or
  equal to the highest already accepted is rejected as replayed or reordered,
  by counter number, before any decryption is attempted.
- The counter is on the wire so a receiver can name the failure —
  _"replayed or reordered frame 41, expected > 57"_ — instead of reporting an
  opaque decrypt error. Tampering with it is still caught, because it feeds the
  nonce and any change makes authentication fail.
- The receiver advances its high-water mark **only after** a frame authenticates,
  so a forged high counter cannot lock out the legitimate stream.
- A decryption failure is reported opaquely as _"Sealed frame failed
  authentication"_: a tampered frame and a wrong key are the same event as far
  as the peer is concerned, and the connection dies either way.

Both ends use WebCrypto (`globalThis.crypto.subtle`), present in browsers and in
Node 22+, so the browser and the CLI run byte-identical code rather than two
implementations that have to be kept in agreement.

Fresh sealer and opener counters — and, since 0.7.0, a fresh salt and therefore
a fresh subkey — are created per connection. The maximum plaintext per frame is
1 MiB.

## Registering the tunnel

The CLI holds one outbound WebSocket to `WS /v1/agent`. Registration is a signed
challenge, not a token:

1. Broker sends `tunnel:challenge` with a fresh 32-byte nonce. **Server-issued
   on purpose** — if the CLI chose it, a captured registration frame could be
   replayed forever to impersonate the device.
2. CLI replies `tunnel:register` with its device id, Ed25519 public key, the
   challenge, and a signature over it.
3. Broker answers `tunnel:ready` with a tunnel id, stable across reconnects so a
   reconnecting agent replaces its socket without invalidating the tunnel id
   already sealed into paired browsers' descriptors.

A browser then opens `WS /v1/tunnel/:id`, the broker sends the agent
`stream:open`, and `stream:frame` messages carry sealed payloads in both
directions until a `stream:close` or `tunnel:closed`.

## Matching a stream to its keys

One agent serves every browser paired with this machine, each with its own key
schedule, all multiplexed over one tunnel. The broker deliberately does not know
which pairing a stream belongs to — making it say would hand it exactly the
mapping the design denies it.

So the first frame decides: whichever key schedule authenticates it owns the
stream. AES-GCM's tag is exactly the right discriminator. A stream no key opens
is refused rather than forwarded, which is also what stops an unpaired browser
that guessed a tunnel id from reaching the relay. Trial decryption derives a
candidate subkey per keyring entry from the salt on that first frame, so the
per-connection key costs the agent nothing it was not already doing. The keyring
is capped at 64 pairings, oldest evicted first, which bounds both the cost of trial decryption
and the work an unpaired caller can make the agent do.

## Quotas

Per tunnel, enforced by the broker, configurable:

| Limit                            | Default            | Variable                 |
| -------------------------------- | ------------------ | ------------------------ |
| Bytes forwarded, both directions | 1 GiB              | `API_TUNNEL_MAX_BYTES`   |
| Lifetime                         | 720 minutes (12 h) | `API_TUNNEL_MAX_MINUTES` |
| Concurrent streams per tunnel    | 16                 | `API_TUNNEL_MAX_STREAMS` |

Exceeding bytes or lifetime closes the tunnel with `tunnel:closed` and reason
`quota-exceeded`. The other reasons are `agent-gone`, `expired`, `revoked` and
`server-error`.

The stream cap behaves differently: a `stream:open` beyond the limit is simply
refused rather than killing the tunnel. It is a denial-of-service bound — the
broker allocates per stream, and without a ceiling one browser could open them
without limit.

When accounts are enabled the broker also ties a tunnel to its owner's plan, so
monthly relayed bytes are metered against [the plan limits](/docs/accounts#plan-limits).
With no database configured every tunnel is anonymous and unmetered.

## What the broker holds

Mailboxes, claims and live tunnel sockets — in memory, in one process. That is
why the hosted deployment runs it in PM2 **fork** mode with a single instance: a
second worker would route a browser to a process that has never heard of its
pairing.

It holds no key that can open a frame, and it is not on the direct path at all.
