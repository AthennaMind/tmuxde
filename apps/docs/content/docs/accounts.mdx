title: Accounts and Multiple Servers
description: What signing in adds, and why anonymous pairing keeps working forever.
---

An account is **optional**. Everything on the [pairing](/docs/pairing) page
works with no account, no email address and no network beyond the broker itself.
This page is about what you get if you do sign in, and — just as importantly —
what does not change if you never do.

## What stays the same without one

- `mtmux` serves your tmux.
- `mtmux start` works with no broker at all — that is the default.
- Six-digit pairing works anonymously and always will.
- The sealed tunnel works anonymously.
- `mtmux devices` lists and revokes paired browsers — those records are local to
  the machine, not account records, so the command works offline.

Being signed in is never worse than being anonymous. If registration fails —
expired card, network drop, broker outage — the machine keeps serving its own
terminal. The registry is a convenience layered on top, never a licence check.

## What signing in adds

- **A dashboard.** Your machines in one list instead of one code per machine.
- **`mtmux servers`.** The same list from the terminal, with online status.
- **Named machines.** `mtmux start --name "build box"` instead of a hostname.
- **A liveness signal.** A signed-in server heartbeats the registry every 30
  seconds so the dashboard can show it as online.
- **Ask to join from the browser.** Pick a machine from the dashboard instead of
  reading a fresh code off a screen. Someone still has to say yes, and they can
  say it from wherever they are: a phone already connected to that machine gets
  an in-app prompt showing the device, the account and a six-digit SAS to
  compare, and there is still the prompt in `mtmux start`'s own terminal and
  `mtmux approve` in another shell. Whoever answers first decides. Nobody
  answering means no.
- **More machines.** Free registers one; Pro lifts that.
- **A free 7-day Pro trial.** It starts by itself the first time Free is not
  enough — no button, no card. If you never hit a limit, it never starts.

<Callout type="warn">
  Signing in does **not** give you more relayed traffic. It is the other way
  round: anonymous relay traffic is unmetered, and an account is what introduces
  the monthly meter in the table below. The reason to sign in is the dashboard
  and the machine list, not bandwidth.
</Callout>

## Plan limits

Every limit in the product lives in one table, `packages/config/src/plans.ts`,
so pricing is a diff to one file rather than a hunt through the broker for a
hard-coded number.

| | Free | Pro |
| --- | --- | --- |
| Registered servers | 1 | unlimited |
| Trusted browsers per server | 3 | unlimited |
| Relayed traffic per month | 5 GB | 200 GB |
| Tunnel session length | unlimited | unlimited |
| Rename a server | — | yes |
| Price | free | $10/month or $100/year |

**Free is generous on purpose.** The thing that costs money is relayed bytes, so
that is what is metered — and the local and LAN paths never touch the hosted
infrastructure at all, so they are unmetered by construction. A limit anywhere
else would only teach people the tool is crippled.

The prices above are for display. The authoritative ones live with the payment
provider, and the checkout you actually see is theirs.

## Signing in

```bash
mtmux login
```

This is **OAuth device authorization**, chosen so a headless box can sign in.
The CLI prints a verification URL, a QR for it, and a user code, then waits for
approval. Approve it from any browser — including one on a different machine.

```bash
mtmux whoami     # account, plan, and which broker issued the session
mtmux logout     # sign out on this machine
```

`logout` says it out loud: pairing and tunnelling still work afterwards.

`login` notices an existing session and re-validates it before claiming you are
already signed in — a stale token falls through to a fresh sign-in rather than
making you work out that "already signed in" was a lie.

## Accounts are scoped to a broker

A session is stored against the broker that issued it. Point the CLI at a
different `--api` or `MTMUX_API_URL` and you are anonymous there until you sign
in again.

This is deliberate. A token minted by `api.mtmux.com` means nothing to a
self-hosted broker, and silently sending it there would be both useless and a
credential leak to a third party. Switching brokers means signing in again,
which is the honest behaviour.

## Registering a machine

`mtmux start` registers with the account automatically when one is present,
sending the name, the device public key, the hostname, the platform and the CLI
version. If the plan does not allow another machine, the CLI prints the reason
and an upgrade link and carries on serving — it does not exit.

```bash
mtmux start --name "build box"
```

The name is persisted, so subsequent runs on that machine keep it. Without one
it defaults to the hostname.

```bash
mtmux servers
```

```
  ● build box    online       linux-x64
  ○ thinkpad     3h ago       linux-x64
```

Online means a heartbeat inside the configured window (90 seconds by default).

## Upgrading

```bash
mtmux upgrade
```

Opens a checkout link from the broker, printing it and a QR alongside. It
deliberately does not render prices or take a payment in the terminal: the
authoritative price, the tax treatment and the payment methods all live with the
payment provider, and a number printed here would be a second source of truth
that goes stale silently.

## Accounts on a self-hosted broker

The accounts layer is a separate, optional piece of the broker. **The absence of
a database URL is a supported configuration**, not an error: the endpoints below
answer `503` and pairing carries on untouched. A self-hoster who wants anonymous
pairing needs to configure nothing here at all.

The broker serves these when `DATABASE_URL` is set:

| Route | Purpose |
| --- | --- |
| `/api/auth/*` | better-auth, including the device-authorization grant `mtmux login` uses |
| `GET /v1/me` | The signed-in account and its plan |
| `GET /v1/servers` | Machines on the account |
| `POST /v1/servers/register` | Claim a registry row for a machine |
| `POST /v1/servers/:id/heartbeat` | Liveness |
| `PATCH` / `DELETE /v1/servers/:id` | Rename or remove a machine |
| `GET /v1/billing` | Plan and usage |
| `POST /v1/billing/checkout` | Start a checkout |
| `POST /v1/billing/portal` | Open the billing portal |

Configuration — `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`,
`APP_ORIGIN`, `AUTH_COOKIE_DOMAIN` and the `DODO_*` billing keys — is documented
in [Configuration → Hosted accounts](/docs/configuration#hosted-accounts-optional).
