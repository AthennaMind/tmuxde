mtmux gives a browser a terminal on your machine. This page describes the
authentication model as implemented, not as intended.

## Three credentials, not one

| Credential              | Lifetime                                                            | Where it lives                                                    | How you get one                                            |
| ----------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------- |
| **`AUTH_TOKEN`**        | Forever, until rotated                                              | `~/.mtmux/config.json`, mode `0600`                               | Generated on first run — 32 random bytes                   |
| **Session token**       | 24 hours in the relay; a pairing-derived one is replayed on restart | Relay memory; pairing-derived ones also in `~/.mtmux/config.json` | Redeeming a local pairing offer, or derived from a pairing |
| **Local pairing offer** | 24 hours as `mtmux start` arms it                                   | Nowhere on disk (hashed in relay memory)                          | The QR and the six digits on a local server                |

The point of the second and third is that **the long-lived token never has to be
typed, and never crosses the network.**

### AUTH_TOKEN

The machine's own credential. It authenticates the WebSocket, `GET /file`, and
the loopback endpoint that registers derived tokens.

- Generated as 32 random bytes on first run. `mtmux token rotate` replaces it
  while deliberately preserving the device key and every paired peer.
- Compared by hashing both sides with SHA-256 and then `timingSafeEqual`, so a
  comparison cannot be timed to recover it byte by byte.
- The relay **refuses to boot** with the default or an empty token when bound to
  a non-loopback address. On loopback it is allowed, which keeps local
  development friction-free.

### Session tokens

Scoped, short-lived credentials that stand in for `AUTH_TOKEN`.

- Issued by redeeming a LAN pairing nonce, or derived independently by both
  sides from a completed PAKE.
- The relay stores them as a **SHA-256 digest only**, in memory, with an expiry
  — default 24 hours.
- Registered through `POST /_pair/session`, which is **loopback-only**, requires
  `Authorization: Bearer <AUTH_TOKEN>`, caps the body at 1 KB, and requires the
  token to be at least 32 characters.

**Two lifetimes, and the difference matters:**

- A **LAN nonce** sign-in exists only in relay memory. Restarting mtmux signs it
  out.
- A **pairing-derived** token is also written to `~/.mtmux/config.json` against
  its peer record, and `mtmux start` replays it on boot. Restarting mtmux does
  _not_ sign that device out — it stays trusted until it goes 90 days unseen or
  you revoke it. This is the point of pairing, and it means a restart is no
  longer a blunt revocation tool for those devices. It adds no secret to a file
  that was not already holding the machine's auth token and Ed25519 secret key.

<Callout type="warn" title='Be precise about "scoped"'>
  These tokens are scoped in *time* and to a single pairing. They are **not**
  scoped by capability: a session token authenticates the WebSocket exactly as
  `AUTH_TOKEN` does and can perform every operation the protocol offers. Treat
  one as equivalent to the machine token for the 24 hours it lives.
</Callout>

### The local pairing offer

The mechanism behind "no token to type" on your own network. One offer, two
spellings: a 128-bit nonce in the QR, and six digits to type.

- Single-use, and **burned on redemption** whether or not the caller does
  anything with the token it receives. Spending either half spends both, so a
  photograph of the QR cannot outlive digits somebody has already typed.
- Only one is live at a time — arming a new one clears the previous.
- Redeemed at `POST /_pair/local`. `GET` is refused with `405`, on purpose: a
  `GET` would put the credential in access logs and `Referer` headers.
- `Content-Type: application/json` is **required**. That is a CSRF control, not
  a parser nicety: a JSON body is not a "simple request", so a cross-origin
  `fetch` has to preflight and this origin answers no preflight. Without it, a
  page on the open internet could spend guesses through the browser of anybody
  sitting on your wifi — it could never read the answer, but it would not need
  to.
- The nonce travels in the URL **fragment** (`/login#n=…`), which browsers never
  send to a server.

The six digits are the part that needs an argument, because a million is a small
number. Four things bound it, and the code's own entropy is the weakest of them:

- **No route from the internet.** This endpoint is only reachable from the
  machine or its network.
- **Five wrong guesses and the offer is burned.** The terminal says so and
  prints a fresh one.
- **The same per-address backoff that guards token authentication.** Five
  rejections, then 30 seconds, doubling to fifteen minutes; a success clears it.
  Without this, burning and re-arming would just hand an attacker five fresh
  guesses at a time, and the whole space would fall in an afternoon. With it,
  the same search runs for centuries.
- **A human still has to say yes.** A correct code raises the approval question
  on the machine, exactly like every other path. Knowing the code is not
  consent.

An unknown, spent, expired or wrong credential gets a generic `401` — _"Pairing
code is invalid or already used"_ — and the log line carries no credential
material. A refusal at the machine gets `403` instead, because "invalid or
already used" would send somebody whose code was right hunting for a typo that
does not exist; that distinction leaks nothing, since you only reach it by
already knowing the code.

The offer is burned **before** the human is asked. A correct code left live
while the question sits on screen is a code an attacker can retry the instant it
is denied.

## Connecting

Authentication is the **first message** on the WebSocket, not a header or a
query parameter:

```json
{ "type": "auth", "token": "…" }
```

- Anything else as the first message is refused.
- There is a **5-second deadline**. A socket that has not authenticated by then
  gets `auth:failure` and is closed.
- Either `AUTH_TOKEN` or a live session token is accepted.
- On success the relay replies `auth:success` and a `server:info` frame.
- On failure it replies `auth:failure` with a reason and **closes the socket**.

### A valid token is not permission

Authenticating gets a socket as far as the door. Whether it comes in is a
separate question, put to a human at the machine — the app on a device already
connected, the terminal or live panel, or `mtmux approve` — and asked of
**every** connection: loopback, LAN and tunnelled alike. Silence denies.

This is the one check that is not about a credential. A credential is a file on
somebody else's computer; that it paired once is a fact about the past. The
question here is whether the person holding it now is you, and it can only be
asked now.

- Nothing about the machine is sent before the answer — no capabilities, no
  hostname, no session names. A refusal reveals only that the token was not
  enough.
- One answer covers a device while it stays connected, and for two minutes
  after its last socket closes. Tabs, the candidate race and a reconnect on a
  train are one act of connecting, not eight.
- A pairing approval covers the socket it was granted for, so nobody is asked
  the same question twice thirty milliseconds apart.
- A refusal carries `code: "unapproved"`, which tells the browser its
  credential is healthy. Without it, a slow answer would wipe a working pairing
  and send the user back to pairing from scratch.
- `reconnectPolicy` decides whether a device you already trust is asked. It
  defaults to `confirm` with a terminal attached and `trust` without one — see
  [the CLI reference](/docs/cli#mtmux-config).

## Failed-auth throttling

Per remote address, in memory.

- The first **4** failures are free.
- From the **5th**, a lockout starts at **30 seconds** and doubles on every
  further failure, up to **15 minutes**.
- During a lockout, _even a correct token is refused_ — otherwise the lockout
  would be a free oracle telling an attacker when they had guessed right.
- One success wipes that address's history entirely.
- The client is told `retryAfterMs`, then disconnected. Reconnecting is allowed;
  every auth attempt is simply refused until the lockout expires.

Two caveats worth knowing:

- The throttle keys on the socket's remote address. Behind the tunnel every
  connection arrives from loopback and therefore shares one bucket.
- It is wired into WebSocket auth only. Nonce redemption, the loopback session
  endpoint and `GET /file?token=` are not throttled by it.

## Connection limits

| Limit                                       | Value                              |
| ------------------------------------------- | ---------------------------------- |
| Total concurrent connections                | 100                                |
| Concurrent connections per address          | 10                                 |
| Max WebSocket frame                         | 1 MiB                              |
| Inbound messages per second, per connection | `WS_RATE_LIMIT`, default 100       |
| Idle disconnect                             | `IDLE_TIMEOUT_MINUTES`, default 30 |

Over-cap upgrades are closed with WebSocket code **1013 Try Again Later**.
Exceeding the message rate drops that message with a `RATE_LIMITED` error rather
than disconnecting.

After authentication the relay pings every 30 seconds and terminates a peer that
missed the previous pong.

## Pairing security

The full argument is in [How pairing works](/docs/pairing) and
[The sealed tunnel](/docs/sealed-tunnel). In brief:

- The pairing code is **slot(3) + secret(6)**. The secret never reaches the
  broker, not even as a hash.
- Both halves are drawn by **rejection sampling**, so the guessing bound is not
  weakened by modulo bias.
- A code is **single-use**, and a failed key confirmation destroys the mailbox.
  One wrong guess costs the attacker the whole code, and burning one is visible
  to you.
- The broker charges a claim **when it attaches a socket**, and the two ceilings
  that bound guessing — **4 per minute against one slot** and **200 per minute
  service-wide** — deliberately ignore the caller's address. A limit that
  depends on how many addresses an attacker controls is not a limit. The per-IP
  numbers (5 claims, 10 mailboxes per minute) bound allocation, not guessing.
- Tunnel traffic is **AES-256-GCM** under a **per-connection subkey**, derived
  by HKDF from the per-direction session key and a 16-byte salt sent in the
  clear on each direction's first frame, with a strictly increasing counter. A replayed or reordered frame is rejected by number; a
  tampered one fails authentication and closes the connection.
- The browser is never told `AUTH_TOKEN`. It either derives a session token from
  the pairing, or needs no token at all on the tunnel path.

## File access

`ALLOWED_PATHS` is the boundary. Enforcement resolves symlinks on both the
target and each allowed root before comparing, so a symlink pointing out of an
allowed directory does not escape it. Every read, write, create, delete, rename,
upload and watch passes the same guard, and the relay refuses to delete an
allowed root itself.

```bash
mtmux start --allowed-paths /home/me/projects,/var/log
```

Keep it as narrow as the job needs. Fixed size caps apply: 100 KB truncating
read, 1 MB write, 10 MB upload. A partial upload is unlinked if it goes over or
if the client disconnects.

## Origins

The WebSocket upgrade checks `Origin` against `CORS_ORIGINS`:

- No `Origin` header — allowed. Native and CLI clients do not send one.
- Empty `CORS_ORIGINS` — allowed. This means "no restriction", not "reject
  everyone", and is what CLI single-port mode uses because everything is
  same-origin there.
- Otherwise, exact string membership.

The relay never emits a wildcard `Access-Control-Allow-Origin`. In production it
refuses to boot with a `localhost` origin in the list.

## Scoped shares

`mtmux share` narrows a browser's credential to named tmux sessions. Read-only
is a real boundary; read-write is not. The difference, and why, is on its own
page: [Sharing a session](/docs/sharing).

A recordings-scoped share is narrower still: it names `.cast` files and no
sessions at all, so the connection can attach to nothing, send no input and read
no files. The relay refuses every message type outside listing and fetching,
checked against an allow-list so a message type added later is denied by
default. What such a share cannot do is be taken back — see
[Recording a session](/docs/recording).

## Recordings on disk

A `.cast` contains every byte that was on the screen, which routinely includes a
secret something printed. `~/.mtmux/recordings/` is `0700` and each file is
`0600`, and that is the whole of the protection: there is no redaction pass,
because a terminal stream is unstructured and a filter that catches most secret
formats invites trust it has not earned. Recordings are output only — mtmux
never writes asciinema's input event type, so a recording is not a keylogger.

## The device lock

A browser that has paired holds keys in IndexedDB. By default they are stored in
the clear, which is fine on a device only you use and is not fine on a phone you
hand to someone. Setting a PIN in Settings encrypts them.

This is encryption at rest, not a UI overlay — the keys are sealed with
AES-256-GCM under a master key that exists only in memory, and locking is
dropping that key. A reload is always locked, because a JavaScript module
variable does not survive one.

**What a PIN is worth, honestly.** Behind PBKDF2-SHA256 at 600,000 iterations, a
six-digit PIN is roughly a minute of offline guessing on one consumer GPU. It
stops the person holding your unlocked phone — the realistic threat — and it does
not stop someone who copies this browser's storage and takes it away.

**A passkey does.** Its secret comes from the WebAuthn `prf` extension, has 256
bits of entropy, and never leaves the authenticator. It is additive: the PIN
stays the base factor, because neither WebAuthn nor `crypto.subtle` exists on a
plain-HTTP LAN address and `mtmux start` prints exactly such a URL.

**There is no recovery.** Deliberately, and it costs little: re-pairing is
running `mtmux` on the machine and typing one code. Nothing on the machine is
lost — the tmux sessions never stopped.

Individual sessions can be marked **"require unlock to open"**, which re-asks for
the PIN even on an already-unlocked device. The flag lives _inside_ the encrypted
record, so a locked device cannot be inspected to learn which sessions were worth
protecting. It is a privacy control against someone in the room, not a server-side
boundary — anyone with a devtools console on an unlocked device can drive the
socket directly.

## Transport

The CLI serves plain HTTP. That is correct on loopback and on a trusted LAN, and
the pairing flows are designed so no long-lived secret crosses the network even
there.

**Do not expose the port directly to the internet.** Either use the sealed
tunnel — which is end-to-end encrypted regardless of what the transport does —
or put the single port behind a reverse proxy that terminates TLS. See
[Self-hosting](/docs/self-hosting).

## Practical checklist

1. Let mtmux generate the token. Do not invent one by hand.
2. Keep `~/.mtmux/config.json` at mode `0600` — [`mtmux doctor`](/docs/doctor)
   checks this.
3. Narrow `ALLOWED_PATHS` to what you actually need.
4. Remove it with `mtmux devices remove <id>`, then restart to drop any socket that
   device still holds. A restart alone no longer un-pairs anything.
5. Never put the raw port on the public internet without TLS in front.
6. In split deployments set `CORS_ORIGINS` to your exact production origin.
7. Read a recording before you share it. `mtmux record share` hands over a copy,
   and a copy cannot be revoked.
8. Keep mtmux current — `npm install -g mtmux@latest`.
