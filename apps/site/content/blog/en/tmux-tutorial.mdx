tmux is a terminal multiplexer: one program that runs shells and other programs inside
persistent sessions that survive your terminal closing. You start a session, split it into
panes, detach when you need to walk away, and reattach later to find everything exactly as you
left it. This tutorial goes from nothing installed to a working daily setup.

## How do you open tmux?

You open tmux by typing `tmux` at a shell prompt and pressing Enter. There is no application to
launch and no icon to click: the command starts a background server on first use, creates a
session, and attaches your current terminal to it. On macOS and Linux any terminal emulator
works — Terminal.app, iTerm2, GNOME Terminal, Alacritty — though Macs need a little extra setup
for the clipboard and true color, which [tmux on Mac](/blog/tmux-on-mac) covers. On Windows
there is no native tmux, so
you open a WSL shell first and run `tmux` inside that; [tmux on Windows](/blog/tmux-on-windows)
covers the setup.

If the shell answers `tmux: command not found`, nothing is broken — tmux just isn't installed
yet, and [installing tmux](/blog/install-tmux) covers every package manager.

Bare `tmux` opens an unnamed session, which tmux numbers `0`. That's fine for a first look and
annoying by the third one, because `tmux ls` ends up listing `0`, `1`, `2` and you have to guess
which is which. `tmux new -s work` names it instead, and a named session is one you can find
again later — [tmux new session](/blog/tmux-new-session) has the full argument for that habit.

Leaving tmux is the part beginners get wrong. Press <Cmd>Ctrl-b</Cmd> then <Cmd>d</Cmd> to
detach: the session and everything in it keeps running. Closing the terminal window does the
same thing by accident but tells you nothing, and typing `exit` closes the pane for good.

One disambiguation, since the string turns up in searches: "OpenTmux" is also the name of an
unrelated OpenCode plugin. If that's what you were after, this page is not it.

## The mental model

Four words explain almost everything that confuses people about tmux: **server, session,
window, pane.**

<CompareTable
  columns={["Level", "What it is"]}
  rows={[
    ["Server", "One background process per machine, started automatically by your first tmux command"],
    ["Session", "A named container of windows — the thing that survives you disconnecting"],
    ["Window", "A tab inside a session, with its own name, shown in the status bar"],
    ["Pane", "A split within a window — one window can hold several panes side by side or stacked"],
  ]}
/>

The relationship is strictly nested: a server runs many sessions, a session holds many windows,
a window holds many panes. Nothing above the server level is shared between machines — a
session lives entirely on whichever machine started it, which is why attaching over SSH puts
you back in the same place even after your laptop sleeps and reconnects.

If you only take one thing from this section: **detaching is not closing.** Closing your
terminal window while attached to tmux over SSH just drops the connection — the session, and
everything running in it, keeps going on the server.

<Callout type="note" title="Install first if you haven't">
This tutorial assumes `tmux -V` already prints something. If it doesn't,
[installing tmux](/blog/install-tmux) covers every major package manager and building from
source.
</Callout>

## Your first session

<Steps>
<Step title="Start tmux">
Run `tmux new -s intro` in a terminal. tmux takes over the screen, draws a status bar at the
bottom (or top, depending on config), and drops you into a shell — the same shell you'd have
gotten without tmux, just running inside a pane now.
</Step>
<Step title="Notice what didn't change">
Type a command, run `ls`, do anything you'd normally do. Nothing about how the shell behaves is
different. tmux doesn't intercept your keystrokes except for one specific chord, covered next.
</Step>
<Step title="Learn the prefix key">
Every tmux command that isn't typed at a shell prompt starts with the prefix key: <Cmd>Ctrl-b</Cmd>
by default. Press and release it, then press a second key. <Cmd>Ctrl-b</Cmd> <Cmd>d</Cmd> means
"prefix, then d" — two separate keypresses, not a three-finger chord.
</Step>
<Step title="Detach">
Press <Cmd>Ctrl-b</Cmd> then <Cmd>d</Cmd>. Your terminal returns to a normal shell prompt, and
prints `[detached (from session intro)]`. The session is still running — you just stepped away
from it.
</Step>
</Steps>

<TerminalDemo title="~ — first session, first detach">
$ tmux new -s intro
# ... press Ctrl-b then d ...
[detached (from session intro)]
$ tmux ls
intro: 1 windows (created Mon Jul 10 09:00:00 2026)
</TerminalDemo>

## Your first split

Panes are where tmux stops being "a session that survives disconnects" and starts being
genuinely useful day to day — running an editor and a server side by side, in one window,
without switching applications.

<Steps>
<Step title="Reattach">
`tmux attach -t intro` (or the shorthand `tmux a` if it's your only session) puts you back
exactly where you detached.
</Step>
<Step title="Split vertically">
<Cmd>Ctrl-b</Cmd> then <Cmd>%</Cmd> splits the current pane into two, side by side. The `%`
looks like a vertical divider if you squint, which is the entire mnemonic.
</Step>
<Step title="Split horizontally">
<Cmd>Ctrl-b</Cmd> then <Cmd>"</Cmd> splits the current pane into two, stacked. `"` looks like
two marks stacked on top of each other.
</Step>
<Step title="Move between panes">
<Cmd>Ctrl-b</Cmd> then an arrow key moves focus to the pane in that direction. Whatever pane has
focus is the one your keystrokes go to.
</Step>
<Step title="Zoom a pane">
<Cmd>Ctrl-b</Cmd> then <Cmd>z</Cmd> expands the current pane to fill the whole window without
changing the layout underneath. Press it again to restore. This is the single most useful pane
binding once you have more than two panes open — zoom in to read a full stack trace, zoom back
out.
</Step>
</Steps>

## Detach and reattach, for real this time

The point of all of the above is a workflow, not a party trick. Start something long-running,
detach, come back later — from the same terminal, a different terminal, or a different machine
over SSH — and reattach:

<TerminalDemo title="~ — the actual workflow">
$ tmux new -s build
$ npm run build:watch
# ... Ctrl-b d, close the laptop, go to lunch ...
$ ssh this-machine
$ tmux attach -t build
# build:watch is still running, output still scrolling
</TerminalDemo>

This is the entire reason tmux exists. A process started in a normal terminal dies when that
terminal closes (technically: it receives `SIGHUP`). A process started inside tmux keeps
running because it's a child of the tmux server, not of whatever terminal you happened to
attach from. [tmux attach session](/blog/tmux-attach-session) goes deeper on what happens when
you reattach with a differently-sized terminal, which is the next thing people trip on.

## A minimal, sensible `~/.tmux.conf`

You don't need a 300-line config with plugins to get real value out of tmux. This is enough to
fix the handful of defaults that genuinely surprise people — every option below is documented,
with its default, in the [tmux man page](https://man7.org/linux/man-pages/man1/tmux.1.html):

```bash title="~/.tmux.conf"
# Easier-to-reach prefix
set -g prefix C-a
unbind C-b
bind C-a send-prefix

# Start numbering at 1, not 0 — matches the keyboard row
set -g base-index 1
setw -g pane-base-index 1

# New panes open in the current pane's directory, not $HOME
bind '"' split-window -v -c "#{pane_current_path}"
bind '%' split-window -h -c "#{pane_current_path}"

# Only resize a window for clients actually viewing it
setw -g aggressive-resize on

# Reload config without restarting tmux
bind r source-file ~/.tmux.conf \; display "reloaded"
```

Reload it with `tmux source-file ~/.tmux.conf`, or just press <Cmd>prefix r</Cmd> once the
binding above is loaded for the first time.

<Callout type="tip" title="Resist the urge to add everything at once">
Every line in a tmux config is something you now have to remember you changed. Add one thing
when a specific default annoys you, not ten things because a blog post listed them. The config
above is deliberately small.
</Callout>

## The five habits that make it stick

<Steps>
<Step title="Name every session at creation">
`tmux new -s work`, not bare `tmux`. `tmux ls` showing `work` and `scratch` instead of `0` and
`1` is the difference between attaching confidently and guessing. See
[tmux new session](/blog/tmux-new-session) for the full naming story.
</Step>
<Step title="Detach instead of closing">
<Cmd>prefix d</Cmd> becomes the default way you end a terminal session, not `exit` or closing
the window. It costs the same effort and never loses your place.
</Step>
<Step title="Name windows, not just sessions">
<Cmd>prefix ,</Cmd> and typing `api` takes two seconds and turns a status bar full of `zsh zsh
zsh` into something you can actually navigate by glancing at it.
</Step>
<Step title="Learn prefix z before anything fancier">
Zoom is worth more than most plugins. You get a full-screen pane on demand without breaking a
carefully arranged layout.
</Step>
<Step title="Keep prefix ? as your real cheat sheet">
It lists every binding your current config actually has — more accurate than any article,
because it reflects your own `~/.tmux.conf`, not a generic default.
</Step>
</Steps>

## Where to go from here

This tutorial covers the mental model and the workflow; [tmux commands](/blog/tmux-commands) is
the reference table to keep open once the concepts click, grouped by session, window, pane and
copy-mode operations rather than explained step by step. The project's own
[getting-started guide](https://github.com/tmux/tmux/wiki/Getting-Started) is a worthwhile
second pass over the same ground in upstream's words. If tmux is going to run something
long — a build, a dev server, an agent — on a machine you're not always sitting at, checking on
it means either SSHing back in and reattaching, or opening the same session in a browser
instead; [tmux in a browser](/blog/tmux-in-browser) surveys the tools for that. mtmux is one of
them — its [docs](/docs) start with the one-command setup, and the
[mobile notes](https://docs.mtmux.com/web-app/mobile) cover what a tmux pane actually feels like
on a phone screen.

<FAQ>
<FAQItem q="What is tmux used for?">
Running shells and programs inside sessions that keep running after you disconnect. The most
common use is starting a long job over SSH, detaching, and reattaching later without losing
output or having the job killed.
</FAQItem>
<FAQItem q="What is the tmux prefix key?">
<Cmd>Ctrl-b</Cmd> by default, pressed and released before the command key — not held together
with it. Most people remap it to <Cmd>Ctrl-a</Cmd> because it's easier to reach on a standard
keyboard.
</FAQItem>
<FAQItem q="How do I exit tmux without killing my session?">
Detach with <Cmd>prefix d</Cmd>. Typing `exit` or pressing <Cmd>Ctrl-d</Cmd> in every pane
closes the window (and eventually the session) instead — that's the one to avoid if you want to
come back to it.
</FAQItem>
<FAQItem q="How do I split panes in tmux?">
<Cmd>prefix %</Cmd> splits vertically (side by side), <Cmd>prefix "</Cmd> splits horizontally
(stacked). Move between panes with <Cmd>prefix</Cmd> plus an arrow key.
</FAQItem>
<FAQItem q="Do I need a tmux.conf to use tmux?">
No — tmux works fully out of the box. A config file is worth adding once specific defaults
start bothering you (the prefix key, window numbering starting at 0), not before.
</FAQItem>
</FAQ>
