Every tmux command is either a shell command (`tmux something`) or a key binding pressed after the
prefix, which is <Cmd>Ctrl-b</Cmd> unless you changed it. That single distinction explains most of
the confusion beginners have, so it is worth stating before the tables: `tmux kill-session` and
<Cmd>Ctrl-b</Cmd> then <Cmd>x</Cmd> are the same kind of thing, typed in two different places.

This is the reference I actually keep open, grouped by intent rather than alphabetically. If tmux
is not on the machine yet, [installing tmux](/blog/install-tmux) covers apt, dnf, pacman, Homebrew
and building from source; the [official manual](https://man7.org/linux/man-pages/man1/tmux.1.html)
is the exhaustive version of everything below.

## The prefix key, and why everything hangs off it

tmux reserves one chord so the other several hundred keys can still reach the program running
inside your pane. That chord is the prefix. Out of the box it is <Cmd>Ctrl-b</Cmd>.

You press the prefix, release it, then press the command key. <Cmd>Ctrl-b</Cmd> <Cmd>c</Cmd> is
"prefix, then c" — not a three-key chord.

Most people remap it to <Cmd>Ctrl-a</Cmd> because it is easier to reach:

```bash title="~/.tmux.conf"
unbind C-b
set -g prefix C-a
bind C-a send-prefix
```

That last line matters: it lets you send a literal <Cmd>Ctrl-a</Cmd> through to the shell (where it
means "start of line") by pressing it twice.

<Callout type="tip" title="Reload without restarting">
After editing `~/.tmux.conf`, run <Cmd>tmux source-file ~/.tmux.conf</Cmd>, or bind it:
`bind r source-file ~/.tmux.conf \; display "reloaded"`.
</Callout>

Under WSL the prefix works the same, but the terminal in front of it may swallow chords before tmux
ever sees them — [tmux on Windows](/blog/tmux-on-windows) covers which terminals pass what through.

## Session commands

A session is the top-level container. It survives your terminal closing, which is the entire
reason tmux exists.

<CompareTable
  columns={["Command", "What it does"]}
  rows={[

    ["tmux new -s work", "Start a new session called work"],
    ["tmux ls", "List sessions (long form: list-sessions)"],
    ["tmux attach -t work", "Attach to the session called work"],
    ["tmux a", "Attach to the most recent session"],
    ["tmux switch -t api", "Switch the current client to another session"],
    ["tmux kill-session -t work", "Kill one session"],
    ["tmux kill-server", "Kill every session on this server"],
  ]}
/>

And the key bindings for the same operations, once you are already inside:

<CompareTable
  columns={["Keys", "What it does"]}
  rows={[
    ["prefix d", "Detach — leave everything running"],
    ["prefix s", "Interactive session picker"],
    ["prefix $", "Rename the current session"],
    ["prefix (  /  )", "Previous / next session"],
  ]}
/>

The one to internalise is <Cmd>prefix d</Cmd>. Detaching is not quitting: your processes keep
running, and `tmux attach` puts you back exactly where you were —
[attaching has its own sharp edges](/blog/tmux-attach-session) once two clients are involved. The
creation side has more flags than the table above suggests: `-d`, `-c`, `-A` and the trailing
command argument are all covered in [tmux new session](/blog/tmux-new-session).

<TerminalDemo title="mbp — tmux">
$ tmux new -s work
# ... you work, then press prefix d ...
[detached (from session work)]
$ tmux ls
work: 3 windows (created Mon Jul 14 09:12:41 2026)
$ tmux attach -t work
</TerminalDemo>

## Window commands

Windows are tabs inside a session.

<CompareTable
  columns={["Keys", "What it does"]}
  rows={[
    ["prefix c", "Create a window"],
    ["prefix ,", "Rename the current window"],
    ["prefix n  /  p", "Next / previous window"],
    ["prefix 0-9", "Jump to window by number"],
    ["prefix w", "Interactive window picker"],
    ["prefix f", "Find a window by name"],
    ["prefix &", "Kill the current window"],
  ]}
/>

Naming windows is the highest-value habit here. `prefix ,` and typing `api` costs two seconds and
saves you from a status bar reading `0:zsh 1:zsh 2:zsh`. If sessions, windows and panes are still
three words for the same fog, [the tmux tutorial](/blog/tmux-tutorial) builds them up in order
rather than listing them.

## Pane commands

Panes are splits within a window.

<CompareTable
  columns={["Keys", "What it does"]}
  rows={[
    ["prefix %", "Split vertically (side by side)"],
    ["prefix \"", "Split horizontally (stacked)"],
    ["prefix o", "Cycle to the next pane"],
    ["prefix ; ", "Toggle to the last-used pane"],
    ["prefix arrow", "Move to the pane in that direction"],
    ["prefix z", "Zoom the pane to fullscreen, press again to restore"],
    ["prefix x", "Kill the current pane"],
    ["prefix {  /  }", "Move the pane left / right in the layout"],
    ["prefix space", "Cycle through the preset layouts"],
  ]}
/>

<Callout type="note" title="prefix z is the one people miss">
Zoom is the single most useful pane binding. You can keep a four-pane layout and still read a full
stack trace without touching the layout itself — zoom, read, zoom back.
</Callout>

The mnemonic for the splits is that `%` looks like a vertical divider and `"` looks like two stacked
marks. If that does not stick, rebind them to something that does:

```bash title="~/.tmux.conf"
bind | split-window -h -c "#{pane_current_path}"
bind - split-window -v -c "#{pane_current_path}"
```

The `-c "#{pane_current_path}"` part makes new panes open in the directory you were already in,
which is what you almost always want and is not the default.

If you live in vim, `prefix arrow` is one keystroke too many — [tmux and vim](/blog/tmux-vim) covers
making `ctrl-h/j/k/l` move between vim splits and tmux panes without you having to know which one
you are currently in.

## Copy mode

Copy mode is how you scroll, search and select. Enter it with <Cmd>prefix [</Cmd> and leave it with
<Cmd>q</Cmd>.

<CompareTable
  columns={["Keys", "What it does"]}
  rows={[
    ["prefix [", "Enter copy mode"],
    ["/  or  ?", "Search forward / backward"],
    ["n  /  N", "Next / previous match"],
    ["space", "Start selection (vi mode)"],
    ["Enter", "Copy selection and exit"],
    ["prefix ]", "Paste the buffer"],
    ["q", "Leave copy mode"],
  ]}
/>

If those keys feel wrong, you are probably a vim user and tmux is in emacs mode. Fix it:

```bash title="~/.tmux.conf"
setw -g mode-keys vi
bind -T copy-mode-vi v send -X begin-selection
bind -T copy-mode-vi y send -X copy-selection-and-cancel
```

Copying into tmux's own buffer is the easy half. Getting it into the *system* clipboard is
platform-specific and the usual reason "copy doesn't work" —
[tmux on Mac](/blog/tmux-on-mac) covers `pbcopy` and the iTerm2 side of it.

## Commands worth knowing for scripts

These are the ones that make tmux useful from a shell script or a dotfiles repo, and they are
where the shell-command form earns its keep.

<CompareTable
  columns={["Command", "What it does"]}
  rows={[
    ["tmux new -d -s ci", "Create a detached session without attaching"],
    ["tmux send-keys -t ci 'npm test' Enter", "Type a command into a pane"],
    ["tmux capture-pane -p -t ci", "Print a pane's contents to stdout"],
    ["tmux list-panes -a -F '#{session_name}:#{window_index}'", "Machine-readable pane list"],
    ["tmux has-session -t ci 2>/dev/null", "Exit 0 if the session exists — ideal for guards"],
    ["tmux set-hook -g pane-died 'run \"...\"'", "React to a pane's process dying"],
  ]}
/>

`capture-pane` and `has-session` are the two that turn tmux from an interactive tool into
something you can automate around. A dev-environment bootstrap script is usually just
`has-session || (new -d; send-keys; send-keys; ...)`. If you would rather not maintain that script,
[tmux plugins](/blog/tmux-plugins) covers tmux-resurrect and tmux-continuum, which save and restore
the layout for you.

<TerminalDemo title="~/bin/dev — idempotent session bootstrap">
#!/usr/bin/env bash
tmux has-session -t work 2>/dev/null && exec tmux attach -t work

tmux new -d -s work -n editor
tmux send-keys -t work:editor 'nvim' Enter
tmux new-window -t work -n server
tmux send-keys -t work:server 'npm run dev' Enter
exec tmux attach -t work
</TerminalDemo>

## The subset that covers 90% of real use

If you only memorise ten, memorise these:

<Steps>
<Step title="tmux new -s name">Start a named session.</Step>
<Step title="prefix d">Detach and leave it running.</Step>
<Step title="tmux attach -t name">Come back to it.</Step>
<Step title="prefix c">New window.</Step>
<Step title="prefix ,">Name that window.</Step>
<Step title="prefix %  and  prefix &quot;">Split into panes.</Step>
<Step title="prefix arrow">Move between panes.</Step>
<Step title="prefix z">Zoom a pane and unzoom it.</Step>
<Step title="prefix [">Scroll and search the output.</Step>
<Step title="prefix ?">List every binding, when you forget one.</Step>
</Steps>

That last one is the real cheat sheet. <Cmd>prefix ?</Cmd> lists every key binding your config
currently has, which is more accurate than any article — including this one — because it reflects
your actual `~/.tmux.conf`. The
[project's own getting-started guide](https://github.com/tmux/tmux/wiki/Getting-Started) is the
other authority worth bookmarking.

## Reading a session you are not sitting at

The commands above assume you are at the machine. The awkward case is the one where you started a
long run, walked away, and want to know whether it finished.

`tmux capture-pane -p` over SSH works, and for a quick check it is fine —
[running tmux over SSH](/blog/tmux-ssh) has its own failure modes worth knowing. What it does not
give you is the live pane, scrollback and all, on whatever device is actually in your hand. That is
what [tmux in a browser](/blog/tmux-in-browser) is about, and it is the shape of the problem when
the thing you left running is [a coding agent](/agents) rather than a build.

[mtmux](/docs) is one answer: it attaches to the tmux server you already run and serves the same
session to a browser — real keys, real reflow, nothing to port-forward. The
[web terminal reference](https://docs.mtmux.com/web-app/terminal) covers what survives the trip and
what does not.

Either way, the tmux commands stay exactly the same. Nothing above changes.

<FAQ>
<FAQItem q="What is the default tmux prefix key?">
<Cmd>Ctrl-b</Cmd>. You press and release it, then press the command key. Many people remap it to
<Cmd>Ctrl-a</Cmd> in `~/.tmux.conf` because it is easier to reach.
</FAQItem>
<FAQItem q="How do I list all tmux commands and key bindings?">
Press <Cmd>prefix ?</Cmd> inside tmux to list every current binding, or run
<Cmd>tmux list-commands</Cmd> in a shell for the full command set. The in-tmux listing is more
useful because it reflects your own config.
</FAQItem>
<FAQItem q="What is the difference between detaching and killing a tmux session?">
Detaching (<Cmd>prefix d</Cmd>) leaves every process running and lets you reattach later with
<Cmd>tmux attach</Cmd>. Killing (<Cmd>tmux kill-session</Cmd>) terminates the session and
everything running inside it.
</FAQItem>
<FAQItem q="How do I scroll up in tmux?">
Enter copy mode with <Cmd>prefix [</Cmd>, then scroll with the arrow keys or Page Up. Press
<Cmd>q</Cmd> to leave. With `mode-keys vi` set, <Cmd>/</Cmd> searches the scrollback.
</FAQItem>
<FAQItem q="Why do new tmux panes open in my home directory?">
That is the default. Add `-c "#{pane_current_path}"` to your split bindings to make new panes
inherit the current pane's working directory instead.
</FAQItem>
</FAQ>
